## D. Security and financial integrity

The application mounts authenticated administrative Payroll and a separate Staff self-service router. Administrative operations apply PAYROLL_READ or PAYROLL_MANAGE. Admin has read/manage; Superadmin has read; Staff self-service additionally scopes employee identity and published documents. Clients lack Payroll access. A disabled UI control is not used as the backend authorization boundary.

`transitionApproval` locks both the run advisory key and parent row, verifies current calculation ID/revision and run status, requires complete calculated items and prior submission, and rejects the run preparer/calculation author as approver. The approval event and audit writes share the transaction. Repeated operations reject or return existing state according to their operation contract; recalculation intentionally appends a new revision and must not be described as universally idempotent.

The calculator parses decimal strings into bigint cents, applies explicit half-up division for time-based earnings, caps supported amounts, blocks negative net totals/unsupported policies, retains effective-dated compensation and attendance snapshots, and separates incomplete results from known totals. Monthly proration and unpriced overtime are not inferred. The server, rather than a frontend number conversion, persists authoritative values. PDF generation reads the approved revision and its component breakdown.

The approved-snapshot guard covers INSERT/UPDATE/DELETE of calculations, employee items and components; it locks the same run row as approval and rejects parent reassignment. Approved runs and approval/payslip records have their own guards. Role owners/superusers can undermine trigger-based protections: deployed grants remain a deployment requirement, not a passing local assertion. No historical migration was edited.

Simulation requires development mode plus the explicit simulator setting. Generated destinations contain test kind and last-four data; they are not verified real bank accounts. Batch/item and idempotency-key advisory locks plus persisted attempts prevent conflicting repeats. PayMongo execution is disabled in source; credentials do not enable it. The declared future endpoint is not an implemented payment client or production integration.

The changed-file text scan found no candidate live secret key, embedded private key, or non-example remote password URL under its stated patterns. This is a scoped heuristic scan, not a guarantee that every possible secret encoding was detected. Ignored real environment files were not read or printed.
