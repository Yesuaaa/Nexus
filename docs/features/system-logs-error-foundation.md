# Error & Exception Logging foundation (Phase 3A)

Developed: 2026-11-16

Follow-up: [Phase 3B Errors & Exceptions UI](system-logs-error-ui.md) adds an offline-gated reader/view using this foundation. The no-endpoint/UI statements below describe the Phase 3A handoff.

**Backend collection implemented locally; no diagnostic HTTP endpoint or UI. Production System Logs remains disabled.** This extends error collection without modifying management-history adapters, their activation gate, domain writers, database schema, business responses or authorization. [Durable access evidence](system-logs-durable-access-evidence.md) remains a separate unresolved prerequisite: this buffer does not satisfy it.

## Infrastructure and architecture

Inspection reconfirmed the shared Express `handleError`, development response decorator, feature-local boundaries, shared Prisma/read transaction helper and PGlite test infrastructure. Production Compose defines API/web containers without a verified collector or evidence volume; configured Supabase storage is for public service images. No suitable independent logging infrastructure was verified. No provider, queue, dependency, table, migration or new disk volume was introduced.

The minimum store uses existing API process memory: one central collector per process, **1,000 records maximum**, **24-hour maximum queryable age**, newest first. At capacity it evicts the oldest record and increments a saturating eviction counter. Appends and reads prune records whose age is at least 24 hours; an unreferenced timer sweeps every minute when idle. Thus an expired record may remain allocated until the next sweep but is never returned. TTL uses server occurrence time and assumes a reasonably synchronized clock. Retention is an implementation bound for this ephemeral buffer, not a legal retention assertion or the earlier provisional 30-day operational-store proposal.

This is intentionally **best-effort instance-local storage**, not durable or deployment-wide collection. Restart, replacement, crashes and process loss erase records; replicas have independent buffers. There is no offline replay, persistent archive, external index or delivery guarantee. A future UI must disclose these limits, and deployment-wide historical investigation needs a separately approved storage decision. Memory buffering must never be accepted as the durable access-evidence gate.

The shared error handler records resolved 5xx failures before sending its existing response. A request middleware registers a completion listener to capture direct 5xx responses and feature-local boundaries that do not forward errors. A request-scoped WeakMap generates correlation IDs and suppresses duplicate capture by these two paths. Errors after headers are sent are captured while preserving the already committed HTTP status and existing delegation behavior. The existing background message-expiry job records failed internal execution through a bounded enum-only entry point. No blanket console interception or collection of all successful requests was added.

## Structured record and safe read contract

`ErrorRecord` version 1 contains:

| Field                               | Contract                                                                                                                                                                                                                                                                                                          |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `errorId`, `occurredAt`             | Server UUID and UTC millisecond timestamp.                                                                                                                                                                                                                                                                        |
| `category`, `severity`              | `application`, `database` or `internal`; severity currently `error`.                                                                                                                                                                                                                                              |
| `moduleId`, `operation`             | Existing supported module IDs or `platform`; closed operations `http.request`, `messages.expire`, `database.probe`.                                                                                                                                                                                               |
| `code`, `message`                   | Fixed `API_FAILURE`, `DATABASE_FAILURE`, `INTERNAL_FAILURE` and corresponding fixed safe descriptions; never exception text.                                                                                                                                                                                      |
| `method`, `routeTemplate`, `status` | Approved HTTP method or `OTHER`, application-defined route template or null, actual response status. Internal operations use null HTTP context. Templates use trusted Express route metadata and recognized API mount names; actual URL/query/parameter values are not stored. Unknown/unmatched routes use null. |
| `requestId`, `actorId`              | Server-generated correlation UUID; client correlation headers are ignored. Actor ID comes only from existing verified `request.auth`, otherwise null. Internal jobs have null actor. No token/session identity reconstruction.                                                                                    |

Internal records additionally retain an allowlisted database/connection diagnostic code and a retryability flag derived from the existing temporary-database classifier. No raw error object, message, stack, cause tree, body, cookie/header, token, connection string, query, personal field, SQL or arbitrary metadata is retained. These internal fields are excluded from public projections. Request actor IDs are restricted identifiers retained because the requested diagnostic contract requires them; account names/emails are not collected.

The unmounted `listErrorLogs(auth)` service returns version, `scope: instance`, `durable: false`, retention/capacity, failure/eviction counters, `truncated` and at most **100** sanitized newest records. It validates the current persisted session/account, expiry, active/non-retired state and exact `SUPERADMIN` role on every invocation, using shared Prisma read transactions. Stale caller/JWT role claims do not authorize reads. Missing/revoked/expired sessions yield 401, other roles 403, authorization storage failure a generic 503. Repository reads are trusted backend helpers, never an alternative HTTP authorization surface.

No route exposes this service, internal diagnostic codes or buffer status. There is no new production access switch. Existing `/api/system-logs` defaults remain generic 404/no-store. Future HTTP reads still require separately reviewed privacy, access-evidence, cache and release controls.

## Classification and failure policy

- Existing resolved 4xx responses, including validation, authorization, not-found and mapped Prisma conflicts, are skipped. HTTP classification follows the existing response resolver rather than reclassifying expected database conflicts as failures.
- Existing temporary DB detection, approved database error codes and Prisma error types classify database failures; other 5xx requests are application failures. Internal job failures are internal unless recognized as database failures. Wrapped `HttpError` causes may supply classification but are never serialized.
- Direct 5xx responses preserve safe status/module/operation context but have generic application classification when no exception reaches the central handler. Handled failures returning 2xx/4xx, realtime failures, shutdown errors and other background jobs are not universally instrumented. New internal hooks must use closed operation/module values rather than caller-defined messages.
- Recording is synchronous and bounded; no network/database await or retry occurs on the business path. Append, classification or hostile-error-property failures are caught and increment a saturating dropped counter. They never change business response/transaction outcomes or recursively log logging failures. Catastrophic process/OOM failure cannot be contained by this mechanism.
- Existing development diagnostics and console output remain under their existing policies; they are not imported into the buffer or returned through its read service. This phase does not claim to sanitize all pre-existing operator console channels or change existing development response contracts.

## Recommended Phase 3B plan

1. Review the diagnostic HTTP projection, minimized actor identifiers, allowed filters, bounded pagination, cache policy and required durable access evidence. Decide whether instance-local, restart-limited history is acceptable for the UI or approve a separate persistence implementation first. Do not present this buffer as complete cross-replica history.
2. Only after that review, implement an explicitly gated Superadmin reader that reuses current session checks and the existing sanitized contract. Keep the management-history gate/adapters unchanged; no environment flag alone authorizes production exposure.
3. Reuse the System Logs shell/table/filter/detail primitives for an Error Logs view, with instance scope, retention/eviction/truncation and unavailable states visible. Never render raw exception messages or stacks. No operational commands, exports, health probes or repair actions belong to this slice.
4. Test every role, revocation, privacy, bounded pagination, storage loss and responsive error/empty states; separately review deployment storage and production release prerequisites. Future Health & Diagnostics can consume safe codes/modules/operations without changing the domain audit histories.

**Stop after Phase 3A.** No Error Logs frontend, diagnostic read endpoint, external infrastructure, production activation or Phase 3B implementation is included.
