# Employee updates and Department Head actor attribution — Phase 4B.4B.4B

Developed: 2026-11-15.

`PUT /api/employees/:id` now records its authenticated administrative actor and all current material Employee, login-assignment, team-leadership and Department Head effects. No derived effect identified in this execution path is deferred. This implements the Employee update portion of the [attribution design](administrative-mutation-attribution-audit.md), reusing the completed [foundation](administrative-attribution-persistence-foundation.md), [Account](account-management-actor-attribution.md), [Client](client-management-actor-attribution.md), [Employee lifecycle](employee-account-lifecycle-attribution.md), and [Employee creation](employee-creation-profile-attribution.md) integrations.

Standalone Department/Team Management attribution is not implemented. The route retains existing authorization, validation, business decisions, responses, transaction isolation and lock ordering. No schema/migration, permission grant, operational identity, lifecycle behavior, history API/UI, Diagnostics or centralized System Logs is added.

## Scope and actor propagation

The route still requires `requireAuth` and `employees:manage`, currently Admin/Superadmin. Staff, Department Heads and Clients gain no management authority. Superadmin needs no Staff/Employee identity. The controller derives one `createManagementOperation(request.auth!)` after existing input/password checks and passes it through `updateEmployee` into the existing private writer and any displaced-title correction.

The context is optional for internal `updateEmployee` callers: existing creation/lifecycle and standalone department/team paths keep their current behavior and earlier attribution integrations. Only the Employee PUT handler supplies this new update-attribution context. Existing creation, account provisioning and synchronization wrappers are not repurposed or integrated a second time.

All resulting records use `WorkforceManagementChange` with `EMPLOYEE_MANAGEMENT` origin, the actual actor ID and role at authentication, one server-generated operation UUID and database-generated event time. Submitted actor/role/operation/timestamp/history fields do not enter the context. Existing explicit `userId` and password restrictions remain. Employee PUT does not create Account lifecycle or credential events.

Initial status candidate selection, default seniority ordering, explicit replacement selection, nested handoff reservation, return conditions, title-retention tests and staffing/team eligibility are unchanged. No new approval, replacement choice, reassignment or cleanup rule is added. Explicit standalone Department replacement continues to end reservations under its existing rules; that standalone mutation creates no new history in this phase. Its subsequent Employee-return behavior is regression-tested without granting the old Head a new takeover right.

Each actual Department transition is grouped into one record rather than separate duplicate head/tracking events. Mirrored title correction is recorded once and excluded from an extra target profile-position event when that same operation performed the correction. Timestamp-only writes, unchanged fields, unchanged states, and empty no-effect requests produce no history. An empty request that actually repairs existing User profile/assignment synchronization still records those material effects.

## Accurate state and locking

Attribution hooks sit at the existing mutation sites rather than collecting a speculative organization-wide snapshot before authorization or locking:

- The target Employee before-state is the existing re-read after its row lock. Final state is read inside the transaction after all corrections. Profile dates compare by timestamp; personal values are never serialized.
- Current/returning Department snapshots are obtained under the pre-existing status-change Department locks. The corresponding update's returned row supplies after-state.
- Replacement Employee assignment snapshots are selected after the existing replacement row lock. Linked User snapshots are selected after existing User locks and compared with a database re-read following synchronization.
- Title correction uses its existing Employee/User locks and retained-head query. Only when attributed does it select the relevant Employee title before mutation and re-read final title state, recording actual differences without storing title strings. The original helper return semantics remain unchanged.
- On the attributed PUT path, the existing Team lead-clearing `updateMany` uses Prisma's `updateManyAndReturn` equivalent with the same predicate/data. Returned IDs and final `leadId` identify actual affected rows; the predicate proves the previous lead was the target account. There is no unlocked Team pre-read, extra Team locking API, raw SQL, or new Team eligibility rule. Internal non-attributed callers retain the original `updateMany` path.

The route retains its existing transaction isolation; no Serializable upgrade, broader lock acquisition or automatic retry is introduced. Existing lock ordering and target/candidate stale-state guards are preserved. Unrelated business writers are not globally instrumented.

## Atomicity and privacy

All writes and history insertions use the caller's existing Prisma transaction. A failed late event rolls back Employee/profile synchronization, Head/current/temporary relationships, title corrections, team lead/membership effects and earlier events together. Invalid validation/eligibility, authorization, target lookup and database conflicts produce no committed success history. Existing safe Employee DTOs and response/error contracts remain.

The new `employee-update-history.ts` contains only typed, transaction-local projection/comparison helpers for the scoped effects. It is not a generic logger, event bus or history API. Existing history actions, schema and runtime payload allowlists need no extension. Payloads retain approved IDs, fixed HR/employment states, the closed correction cause and changed field names. Passwords/hashes/tokens, raw requests, names/emails/contacts/start-date values, free-form titles and unrestricted database snapshots are excluded. Personal fields needed for equality comparisons remain in memory and are not passed as history values.

HR status remains distinct from User login state. These updates do not revoke sessions or activate/retire logins. Credentials, account role and lifecycle remain unchanged. Superadmin receives no Employee or operational identity.
