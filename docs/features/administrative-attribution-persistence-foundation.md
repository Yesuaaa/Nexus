## Database changes

The additive migration `apps/api/prisma/migrations/20261115030000_management_attribution/migration.sql` creates only:

- `AccountManagementChange`: generated ID, `actorAccountId`, `actorRoleAtTime`, server-generated UUID `operationId`, `subjectAccountId`, `action`, `origin`, `changedFields`, allowlisted JSON `changes`, and database-default `createdAt`.
- `WorkforceManagementChange`: the same attribution fields with `subjectType` and `subjectId` instead of `subjectAccountId`.
- Five closed enums: `AccountManagementAction`, `AccountManagementOrigin`, `WorkforceManagementSubject`, `WorkforceManagementAction`, `WorkforceManagementOrigin`. The existing `Role` enum supplies the actor-role snapshot.
- Six lookup indexes: subject/time/ID, actor/time/ID, and operation ID for each table. Workforce subject lookup includes subject type. Each table also has its primary key.

Account actions are `CREATED`, `PROFILE_UPDATED`, `ROLE_CHANGED`, `STATUS_CHANGED`, `PASSWORD_RESET`, `ARCHIVED`, `RESTORED`, `DELETED`. Workforce actions are `CREATED`, `PROFILE_UPDATED`, `STATUS_CHANGED`, `ASSIGNMENT_CHANGED`, `HEAD_CHANGED`, `TEMPORARY_HEAD_CHANGED`, `LEAD_CHANGED`, `TITLE_CLEARED`, `DELETED`. These classify history; they grant no permissions or new operations.

Account origins are Account, Client, and Employee Management. Workforce origins are Account, Employee, Department, and Team Management. Workforce subjects are Employee, Department, and Team. Runtime validation also checks action/subject compatibility and the narrower existing account action/origin combinations.

Actor and subject IDs are bounded scalar snapshots with **no foreign keys**. Existing User, Employee, Department, Team, and other business relationships are unchanged. Account/subject deletion cannot cascade into these histories or acquire a new attribution-related deletion blocker. These are append-only application writers; the database owner or a direct Prisma/raw-SQL writer can still modify rows. No database tamper-proofing or unrelated database privilege change is claimed.

No backfill, data repair, new synthetic actor, or change to existing records is included. The migration was generated by a schema-to-schema Prisma diff; no live database or shadow database was used. `pnpm db:generate` succeeds with the existing project command.

## Writer interfaces and trust boundary

```ts
const operation = createManagementOperation(request.auth!)
await prisma.$transaction(async (tx) => {
  // A future integration will perform its existing authorized business mutation.
  await writeAccountManagementChange(tx, operation, accountChange)
  // Or writeWorkforceManagementChange(tx, operation, workforceChange).
})
```

This is an integration example, not code wired into a route. The small shared module `apps/api/src/shared/management-history.ts` supplies operation creation and validation primitives for the two domain writers; it is not a logging service, middleware, event bus, or persistence router.

`createManagementOperation(auth: AuthContext)` must receive the trusted `requireAuth` context, never HTTP input or unverified claims. It accepts active, non-retired authenticated Admin/Superadmin snapshots with valid actor/session IDs, projects only actor ID/role, generates the operation UUID on the server, and freezes/registers the result. The operation is reusable across both writers within one business operation. Copies, deserialized objects, and hand-built operation objects are rejected by the writers. Original authentication data, session IDs, and credentials are not retained in history.

This in-process registration is an accidental-forgery guard, not authentication: trusted backend callers remain responsible for obtaining `request.auth` through existing middleware. Writers do not reauthenticate, look up deleted subjects, authorize management actions, compare against business state, enforce workflow eligibility, retry transactions, or implement HTTP idempotency. Role-at-time means the authenticated backend snapshot. Future integrations must preserve existing target authorization and actual before/after state.

`writeAccountManagementChange(tx, operation, input)` and `writeWorkforceManagementChange(tx, operation, input)` use `Prisma.TransactionClient` and append through the supplied transaction. They do not obtain the root database client or start/commit their own transactions. Future callers must supply an actual transaction; TypeScript's structural transaction type is not a runtime proof of transaction membership. Commit and rollback behavior is verified against real offline transactions.

## Payload protection

- Discriminated action payloads and closed enums supply TypeScript contracts. Runtime validation separately rejects unknown top-level keys, unknown actions/origins/subjects, incompatible actions/subjects, unlisted changed fields, duplicate/oversized field lists, missing required transitions, and extra nested fields.
- Transition objects contain exactly `before` and `after`, with approved fixed roles, HR statuses, employment types, booleans, nullable bounded IDs, or canonical lifecycle timestamps. Creation, archive, and restore account payloads enforce their relevant null/non-null direction.
- Metadata is restricted to session-revocation booleans, an approved affected account ID for legacy workforce effects, and the literal `FORMER_DEPARTMENT_HEAD` title-cleanup cause. IDs are 1–80 URL-safe characters, using the existing `isRecordId` utility. Lifecycle timestamps must be canonical ISO UTC milliseconds.
- Profile changes retain field names only for names, email, phone/contact, job title, employee code, start date, department/team descriptions, and similar allowed profile fields. Those values cannot enter `changes`; allowed fixed employment-state transitions are the explicit exception.
- Password-reset history contains only its action/subject/context and `sessionsRevoked: true`. Credential values, password hashes/salts, tokens, raw requests, unrestricted User/Employee snapshots, free-form summaries, and profile values are not accepted. Rejection messages never echo input values.
- Object shapes reject accessors, symbols, custom prototypes, `toJSON`, and unknown nested keys. Values are validated and copied before the single database insert. Payload size is bounded structurally by closed keys, short identifiers, fixed enums, and at most 24 distinct changed field names; no arbitrary text or arrays of record snapshots are allowed.

Approved ID fields remain trusted backend identities, not general-purpose string storage. Shape validation cannot prove that an ID represents the intended historical entity; future authenticated services must supply real subject IDs and accurate transitions. Direct database writes bypass writer validation, as elsewhere in the application. Neither limitation creates a new public endpoint or participant privilege.

## Transactions and deletion

Both records can share one operation ID and one existing management transaction. A thrown application error or failed history insertion rolls back all history and business writes in that transaction. No success event is written outside the transaction, no failed attempt is converted into a success record, and no cleanup occurs on reads.

No operation ID uniqueness constraint is added: a single operation legitimately affects several subjects and actions. Operation grouping is not client retry deduplication. Database-default timestamps are display metadata, not guaranteed global commit ordering. Future integration retains the audit's requirements for stable in-transaction before-images, existing locks/isolation, and accurate bulk/cascade effect capture. Those management concurrency paths are not changed or claimed as validated by this infrastructure phase.
