# Project Management audit integration (Phase 4B)

Developed: 2026-11-16

Follow-up: [Phase 4C Service Operations audit integration](system-logs-service-audit.md) extends the shared workflow source with a separate six-type Service subset and replaces the project-only SQL reader with one union query. The Project policy below remains unchanged; source-wide statements describe Phase 4B's handoff.

**Read-only, metadata-only project event integration for attested offline testing. Production System Logs remains disabled.** This extends [Phase 4A](system-logs-attendance-audit.md) using existing `WorkflowEvent` rows. No project/workflow writer, approval flow, schema, migration, new history or infrastructure is introduced. Activity & Audit reuses its current table, filters, pagination, details and source warnings; Errors & Exceptions and System Health are unchanged.

## Source inspection and module classification

`WorkflowEvent` is a mixed Service Operations/project event stream: it records request ID, nullable actor ID, type, summary, nullable entity ID, internal visibility and creation time. It does not record actor role-at-time or a shared operation ID. Its request association alone does **not** make it a project event. Current `Project`, work plans, milestones, staffing, client reviews, change requests and messages contain current operational state/content and are not alternative histories to synthesize.

The two existing writers below explicitly persist a **project ID** in event `entityId` and have event types exclusive to their project mutations. They provide a suitable minimal existing source without current-state inference:

| Integrated stored type      | Existing writer and provenance                                                                                                                                                                                                                                 | Safe event name                     |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| `PROJECT_MILESTONE_UPDATED` | `projects/projects.service.ts:setMilestoneCompletion` updates an authorized existing milestone in a transaction, then records an event with `entityId: projectId`. It covers completion/reopening through that path, without structured before/after evidence. | `project.project_milestone_updated` |
| `STAFFING_ALLOCATED`        | `workload/workload.controller.ts` allocates existing project staff and records `entityId: projectId` in the same transaction. Hours/name are embedded in summary and are excluded.                                                                             | `project.staffing_allocated`        |

Only **`internal = false`**, non-null entity IDs and these exact allowlisted types qualify. These records belong to Project Management because their persisted type and writer-owned entity semantics identify the project activity, even though the stream also belongs to a request workflow. No live project join, name lookup, current status, request-to-project inference or timestamp heuristic is used. A historical project identifier remains readable if no current project can be found; that does not reconstruct missing event metadata.

Explicitly excluded sources/types:

- Consultation, requirements, quotation, agreement, payment, generic workflow state/hold/closure and migration-initialized request events are Service Operations lifecycle evidence. They are not imported by association with a project's request.
- `PROJECT_ACTIVATED` is emitted from the request's commencement workflow while changing request/workflow/project state. It remains outside this slice rather than silently reassigning that service-to-project transition.
- `WORKSPACE_CREATED`, rename/status/cancellation/task events and task-plan updates are genuine project/workspace activity but are emitted as **internal** by `writeWorkspaceEvent` or its existing setup path. Their internal boundary is preserved; none is collected by this adapter.
- Project cancellation request/decision events are genuine project activity but outside this minimal two-type policy. No complete cancellation or change-request history is claimed.
- Deliverable update/upload/remove/review/share events are excluded. `recordDeliverableEvent` has caller-dependent identity semantics, and sharing can persist a **file ID** in `entityId`; treating every such ID as a project or deliverable would be false. No file, attachment, deliverable or message authority is granted by this viewer.
- Project/client review records, notifications and `WorkflowActionReceipt` are not substitutes for a shared event operation ID. Receipts have a separate request/actor/action identity and no event foreign key; matching them heuristically would fabricate attribution. Unknown/future event types are excluded until reviewed.

## Safe projection and attribution

The new adapter selects exactly **`id`, `createdAt`, `type`, `entityId`, `actorId`, `internal`** from `WorkflowEvent`. It does not SELECT summaries, request IDs, current project rows, names, hours, tasks, work plans, employee/client records, content, messages, files or deliverables. `internal` is a qualification field only and is not exposed. Closed runtime validation rejects unexpected selected fields, malformed/bounded IDs, non-finite timestamps, internal records and non-allowlisted types without echoing source input.

The existing reserved source ID **`audit.workflow`** now has a deliberately narrow integrated subset; its name does not authorize all workflow events. Module is `project-management`, subject is `project` with the stored entity ID. Safe normalized fields are source-qualified audit ID/time, catalog type/action/event name, fixed audit/module/info labels, nullable recorded actor ID and explicit null/empty compatibility fields. `outcome: succeeded` denotes the recorded successful writer path; it does not reveal whether a milestone was completed or reopened, how staffing changed, or overall project success. Those distinctions live in excluded prose/current state and are not inferred.

Actor ID is preserved as stored, including null; no current person or role lookup enriches it. Role-at-time is null with `not-recorded` evidence. Operation/request/trace/action correlation fields remain null because no such event-level correlation is qualified for this slice. Existing normalized `details.kind: project` has null origin, no changed-field/value transitions and no session-revocation value. The project ID is represented by the subject identity; no extra correlation is fabricated.

These events are **ungrouped**, using Phase 4A's existing null-operation behavior and `ungroupedEventCount`. Management operation groups remain unchanged. Project details use the existing SidePanel with a fixed metadata/privacy explanation, **Not recorded** for missing role/operation, and no Investigate operation button. No raw summary or arbitrary JSON rendering is added to any System Logs response.

## Reader, UI and authorization integration

The existing `/api/system-logs/management-history` list and source detail routes are reused; no new endpoint is mounted. Project source/module, subject, exact actor/project ID, approved action/event and existing bounded date/page filters use the established query contract. Explicit project-source operation filters and conflicting modules/actions/subjects fail safe validation. Other sources remain eligible only for compatible filters. The source uses shared Prisma/read-only transactions, parameterized SQL, explicit columns and the same 500-candidate scan cap plus overfetch.

Events participate in the existing global total order `(createdAt DESC, source ASC, id COLLATE C DESC)` and merge **before** page selection. Signed cursors remain bound to current filters, authenticated identity, source set and timestamp boundary. All Modules now includes four qualified sources, not all modules or all WorkflowEvents. An old All Modules cursor bound to the preceding source set fails normal validation instead of silently skipping the new source. Details reuse source/time-window validation. Late commits/backdating and separate source transactions retain earlier documented consistency limits.

Project-source failure is handled independently: project-only outage returns generic 503; a mixed-source request reports explicit unavailability/incompleteness and suppresses continuation. Invalid selected records use existing omission/scan indicators; SQL-excluded types/internal rows are outside supported coverage, not omitted integrated events. No read writes, repairs, backfills or domain side effects are introduced. Existing session activity bookkeeping is unchanged.

Project Management's retained workspace scope is now readable and labelled **Partial — milestone and staffing events**. The scope explanation names only the two non-internal event types and exclusions. Source Filter options includes **Project audit — limited**, with the existing exact event/action/project subject options; the default contextual workspace label, All Modules/Workspace only controls and manual overrides are unchanged. No UI redesign or component/library change is needed.

Existing offline/native-worker/owned-fixture activation checks, shared authentication middleware and independent service-level current-session active/non-retired Superadmin verification remain mandatory. Default development/production composition stays generic 404/no-store; no environment bypass, role expansion or release decision is added. The broader project/workflow participation, attachment and administrative visibility policies are neither reused as diagnostic grants nor modified. Deployed grants/RLS and protected-object ownership remain separate unverified prerequisites.

## Remaining gaps

This is two non-internal event types, not complete project auditing, staffing snapshots, task/deliverable history, cancellation history or project activation coverage. Supporting additional existing event types needs explicit provenance/entity semantics and privacy review; internal events require an explicit separate access decision. Missing project events cannot be recovered from current entities. Future instrumentation, if separately authorized, should transactionally record bounded type, stable subject semantics, authenticated actor/role and explicit operation correlation, without duplicating the existing stream or storing confidential content. This phase does not modify writers to implement that instrumentation.

Existing append-only WorkflowEvent guards, source retention and relational constraints remain as implemented; no deployed role/grant/administrator-resistance claim follows. Additional global source queries retain scan/index/performance limitations: no index, query budget, capacity/SLO qualification or production-scale measurement is added. Durable logs-access evidence, deployed credential/database protection verification and separate release/privacy approval remain outstanding. Current shared-source transactions retain late-commit pagination limits; no cross-request MVCC guarantee is introduced.

**Stop strictly after Phase 4B.** No other module, infrastructure, additional diagnostics or production activation is included.
