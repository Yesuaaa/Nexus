# Service Operations audit integration (Phase 4C)

Developed: 2026-11-16

**Read-only, metadata-only Service Operations workflow integration for attested offline testing. Production System Logs remains disabled.** This extends [Phase 4B](system-logs-project-audit.md) with a six-type subset of existing `WorkflowEvent` records, retaining Client Management account history and the existing two-type Project subset. No writer, business workflow, schema, migration, collector, storage or infrastructure change is introduced. The existing Activity & Audit interface, Errors & Exceptions and System Health remain intact.

## Inspection, supported types and subject policy

The request workflow's existing `event` helper calls `appendEvent(tx, requestId, userId, type, summary, entityId, internal)`. The request identity and actor are supplied by the authorized transactional workflow action, not inferred from a current booking/project. `WorkflowEvent` persists that request ID, nullable actor ID, type, summary, nullable entity ID, internal flag and time; it does not persist role-at-time or a shared operation ID. The existing administrative workflow reader already avoids raw summaries, but its wider type catalog and permissions are not imported as a System Logs allowlist.

Only non-internal records of these types qualify:

| Stored type              | Verified writer/meaning                                                                                                                                                                 | Safe event name                          |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| `CONSULTATION_SCHEDULED` | `workflow.service.ts:SCHEDULE_CONSULTATION` persists a consultation for this request and appends this event. The time/location/notes are excluded.                                      | `service_request.consultation_scheduled` |
| `CONSULTATION_COMPLETED` | `COMPLETE_CONSULTATION` changes a scheduled consultation after its existing authorization/stage/time checks.                                                                            | `service_request.consultation_completed` |
| `CONSULTATION_CANCELLED` | `CANCEL_CONSULTATION` records cancellation of a scheduled consultation; it does not cancel the service request.                                                                         | `service_request.consultation_cancelled` |
| `QUOTATION_SENT`         | Direct published quote creation or `APPROVE_QUOTATION` publishes a quotation for the client's formal decision. Internal-review/approval events remain excluded.                         | `service_request.quotation_sent`         |
| `APPROVAL_CONFIRMED`     | `RESPOND_QUOTATION` with formal client acceptance creates the existing approval and appends this event. No quoted terms, prices, client note, decision payload or document is selected. | `service_request.approval_confirmed`     |
| `WORKFLOW_CANCELLED`     | Existing `CANCEL` action records authorized request-workflow cancellation; the source note is excluded.                                                                                 | `service_request.workflow_cancelled`     |

For these types the **subject is always the persisted requestId**, typed `service_request`. Event `entityId` can refer to a consultation, quotation or approval and is never relabelled as a request or project. It is masked to SQL NULL for Service Operations projections; even its private identity is not transported into normalization/output. No project relation, current request title/status, quote, payment, client, message, document, requirement or booking snapshot is joined. `outcome: succeeded` means the recorded event action completed, not that every request/stage/project succeeded. Formal acceptance occurrence is represented by its approved type; confidential acceptance values are not exposed.

Request/booking submission currently persists the service request (`SUBMITTED`) but this is not itself a qualified event history. No booking-created/request-created event is synthesized from current fields, creation timestamps, receipts or notifications. Consultation scheduling is supported as a workflow activity; this is not calendar/booking-history coverage in general. `CONSULTATION_OPENED` is excluded because the stream includes migration-initialized rows with historical actor/time semantics different from live actions. This avoids presenting initialized state as fresh authenticated action evidence.

## One shared WorkflowEvent source without overlap

The existing `audit.workflow` source now covers two disjoint classifications:

- Project Management: unchanged non-internal `PROJECT_MILESTONE_UPDATED` and `STAFFING_ALLOCATED`, subject from their writer-owned project `entityId` semantics.
- Service Operations: the six exact types above, subject from recorded `requestId`.

`workflowTypes()` pairs **module, subject type, action and event name** per classification. It never constructs a permissive cross-product (such as a Service Operations staffing event or a project quotation event). The new shared `readWorkflowAudit()` performs **one query and one source scan budget** across the qualified union, in the existing total order. It replaces the former project-only query; the original project normalizer remains intact and is called only after removing the extra request projection field. No second source ID/adapter invocation duplicates WorkflowEvent rows. A Service Operations request selects the workflow subset plus existing Client Management Account history; Project Management selects only its existing workflow subset.

The SELECT contains event ID/time/type, nullable actor, internal qualification, stored request ID, and a CASE-projected project entity ID. No summary or confidential source values are selected. Project request IDs are qualification data only and remain absent from the project response, as before. Service request ID is exposed only as the approved subject ID. Source-qualified event identity remains `audit.workflow:<id>` for either classification; module assignment is driven by a verified disjoint type catalog, not the associated request's current state.

The existing four-source cursor/merge/detail architecture is reused: bounded dates/page size, 500 candidates plus overfetch per source, `createdAt DESC, source ASC, id COLLATE C DESC`, shared Prisma read transactions, parameterized SQL, source availability/omission indicators, and merging before page selection. Workflow source read failures affect both workflow classifications; available Client Management rows can still be returned with explicit incomplete coverage and continuation suppressed. Workflow-only failure yields generic 503 rather than an empty complete history.

A **workflow catalog revision marker** is included in the existing signed cursor fingerprint. Previously issued pre-Phase-4C cursors are rejected and must restart from the first page; this prevents a cursor with the same source ID from silently traversing an expanded eligible event set. New cursors remain bound to authenticated identity, filters, catalog/source scope and snapshot. No persistent cursor/session state or activation switch is introduced.

## Attribution, privacy, authorization and UI

The recorded nullable actor ID is preserved. No current name/role lookup occurs; role-at-time stays null/`not-recorded`. The workflow action receipt's separate `actionId` has no event linkage and is not a shared operation/HTTP/trace ID. These events remain null-operation and are counted in the existing explicit ungrouped-event count, not grouped into one fabricated action. Other unqualified correlation fields remain null. No missing actor/operation metadata is recovered from summaries/current entities or invented.

Service details use `details.kind: service` with null origin, empty changed-field/transition containers and null session-revocation value. The shared SidePanel renders a fixed explanation, historical request identity and missing attribution, without an operation-investigation action. Empty transition containers indicate no approved value projection, not an assertion that no underlying fields changed. Raw summaries, quote/version/price/line item/currency data, client communications, reasons/notes, schedules/location, payment details, requirements, files/documents and arbitrary JSON are excluded from System Logs search, responses, details and errors.

Source options now say **Workflow audit — selected request/project events**, accurately covering the qualified union. Service Operations remains **Partial — client accounts and request events**, preserving its existing Client Management account records and automatic originating-workspace scope/manual overrides. Existing source/filter controls, optional exact event search, table, details, badges, counts and incomplete/empty/error states are reused. Subject-type options include `service_request`. No UI redesign or new component library is introduced.

The existing offline/native-test-worker/owned-fixture gate is unchanged. The shared auth middleware and independent service check still require the current active/non-retired Superadmin session; denied role/demotion/inactivity/revocation behavior remains authoritative. Existing service participant/quotation/approval permissions are not diagnostic grants. Normal/default/production composition remains generic 404/no-store, and source/read errors use fixed safe messages. No production access, role change or release decision is added.

## Explicit exclusions and remaining coverage

Excluded: internal notes and approvals (`QUOTATION_INTERNAL_REVIEW`, `QUOTATION_INTERNAL_APPROVED` etc.), requirements/submissions, agreement/document events, payment events, approver assignment, staffing review, commencement/activation, generic hold/resume, rescheduling negotiations, project cancellation/workspace/task/deliverable events beyond the already-qualified Project subset, migration initialization and unknown/future types. A future allowlist extension requires verified provenance, subject semantics and privacy review; current entity state cannot substitute for missing history. This phase does not modify writers to fill any gap.

This is partial event-occurrence metadata, not complete request/booking auditing, client communication access, quote/payment/approval payload access, complete project history or durable access evidence. The existing history lifecycle, immutable guards and foreign-key restrictions remain unchanged and do not attest deployed grants/RLS/ownership or administrator resistance. Additional eligible workflow rows may increase scanning; no index/capacity/SLO qualification is claimed. Separate source transactions and late-commit/backdated cursor limitations remain as documented. Durable logs-access evidence, deployment/credential protections, measured capacity and separate privacy/release approval remain production prerequisites.
