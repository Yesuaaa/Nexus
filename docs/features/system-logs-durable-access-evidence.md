## Minimum access-evidence contract

Use a dedicated closed `LogsAccessEvidenceV1` transport record under the reserved `security.logs-access` source (`category: security`, `area: platform`, `moduleId: null`); this is not a third viewer adapter or a copied history ledger. Validate/redact before transport. Reject unknown fields and records over **8 KiB UTF-8**; never serialize arbitrary request, response or error objects. The following is a proposed contract for implementation, not existing emitted data.

| Field                                           | Required meaning and bound                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `schemaVersion`, `source`, category/area/module | Fixed values above; schema version 1.                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `evidenceId`, `requestId`, `stage`              | Server UUIDs; one request ID per HTTP attempt, separate evidence ID per immutable stage. Stages: `attempt`, `decision`, optional `transport`. Delivery retries reuse the exact stage ID and bytes. Never use client headers as the authoritative ID.                                                                                                                                                                                                                                                    |
| `occurredAt`, `receivedAt`, `authorizedAt`      | Server UTC millisecond occurrence; sink-owned durable receipt time; last successful current-account/session check time or null. `receivedAt` is receipt metadata, not fabricated before acceptance. Synchronize clocks; timestamps alone do not prove order.                                                                                                                                                                                                                                            |
| `actor`                                         | `{accountId, role, verification}` from the current server-resolved account/session only; role is one of the four existing roles. IDs obey the existing record-ID validator. For absent/failed authentication or DB failure before verification, IDs/role are null and verification is `unknown`; never infer identity from token claims. A later failed recheck is explicit in the result. No names, emails or session IDs.                                                                             |
| `action`, `method`, `routeTemplate`             | Closed actions `list`, `event_detail`, `operation_detail`, `unmatched`; GET/HEAD or bounded `OTHER`. Unsupported methods never trigger readers.                                                                                                                                                                                                      |

No exception text or source rows. Attempt uses `requested` and null status; decision reflects the prepared outcome, not a claim of client receipt. |
| `scope`                                         | Null until full query validation succeeds. Invalid input records only a safe rejection code, never partially parsed untrusted scope. Evidence storage and operator searches remain restricted even with these minimized identifiers.

## Durable acknowledgement and disclosure boundary

The future feature-local port is `append(event, deadline, abortSignal) -> DurableReceipt`. A receipt must identify the event, configured destination and payload digest, plus durable acceptance time. The adapter verifies the authenticated destination and provider-specific commit semantics. A process write, health check, queued SDK promise, HTTP 202 or arbitrary 2xx is insufficient without proof that this exact immutable record survived the agreed failure model. An identical pre-existing record may satisfy a retry only after authoritative ID/content verification; a conflicting payload fails closed.

Future orchestration, inside the existing offline gate:

1. Leave the activation latch first and unchanged: normal production/default composition still returns generic 404 without a sink dependency. For the authorized offline path, assign the server request ID, then retain existing auth/role checks and authoritative query validation. Capture fixed denied/invalid/auth-unavailable outcomes at this feature's boundary, including middleware responses; never alter unrelated auth/business routes. Denials retain their existing status even if evidence cannot be stored.
2. For an eligible read, durably acknowledge `attempt` **before source readers run**. Reserve one bounded admission slot first. No transaction or database connection remains open while awaiting the sink. On failure, return generic 503 with `no-store` and no history-bearing metadata.
3. Invoke existing bounded readers/projections with the same validated query used in evidence, including fixed default dates/snapshot. Buffer the bounded response; do not stream, flush headers, or send partial results. Existing service authorization remains. Recheck current session, active/non-retired account and exact Superadmin role after the query; failure suppresses all history.
4. Append and durably acknowledge `decision` with the prepared status and source/completeness result, including partial 200, empty results, not-found, invalid records and unavailable sources. Any acknowledgement failure suppresses the prepared payload and returns generic 503; a partial response never bypasses this requirement.
5. **Revalidate current session/account/role again after acknowledgement and immediately before committing the response.** Revocation/demotion denies disclosure; authentication-DB failure returns generic 503. Record a linked abort when possible, without waiting indefinitely or amending the acknowledged decision. Reuse the existing auth predicates, not stale token roles. Then send the existing projected response with `no-store`.
6. An optional bounded `transport` record reports finish/abort if observable; it is not a prerequisite to bytes already sent. `release_ready` means a prepared release decision, not successful delivery. Even `transport_finished` proves only server transport completion, never client receipt. A final-check failure, disconnect or crash may leave an acknowledged decision without disclosure; missing completion means unknown, not success.

The final check reduces the query/ack wait revocation interval; revocation after that check can still race with network writes. This is an explicit per-request revalidation guarantee, not atomic revocation or exactly-once receipt. Source read transactions, writers, historical null correlation and current partial-page/cursor semantics remain unchanged.

## Failure, retry and recovery requirements

These are **proposed implementation defaults for owner acceptance**, not measured capacity/SLO claims: 16 in-flight evidence-gated reads per API instance, no waiting admission queue, 8 KiB per record; maximum **2 seconds combined evidence wait per request**, including denial/abort stages. Each append permits two total attempts, each at most 400 ms, with 0–100 ms full-jitter backoff before the single retry, subject to the remaining request evidence budget. No new history-query tuning or Phase 2D.3B qualification is implied.

| Condition                                                                | Required behavior                                                                                                                                                                                                                                                                                     |
| ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Storage unavailable, invalid receipt, timeout or exhausted retry         | No source read without attempt acceptance; no history disclosure without decision acceptance. Generic 503/no-store, no fallback success. Late receipt never resumes an ended request.                                                                                                                 |
| Admission limit, provider queue/quota overflow or throttling             | Fail immediately with generic 503 for an otherwise eligible read; do not buffer pending work. A provider queue qualifies only if its own durable acceptance, capacity and downstream preservation are verified. This design introduces no queue.                                                      |
| Transient transport error, ambiguous timeout, retryable provider failure | Retry only the same evidence ID/bytes within the budget. Cancel/abort outstanding work where supported; SDK/internal retries must fit the same limits. Do not retry the HTTP/history response automatically.                                                                                          |
| Payload/receipt conflict, invalid schema, permanent delivery failure     | No blind retry or raw serialization fallback; close the feature's evidence admission and surface a safe failure code to the designated operator mechanism. No recursive evidence-of-evidence loop.                                                                                                    |
| Application DB outage                                                    | Independent sink remains callable; evidence actor is unknown if current identity cannot be established. Preserve denial/no-disclosure behavior. No application-DB outbox or table substitutes for the sink.                                                                                           |
| Crash/restart, sink committed but receipt lost                           | No local replay promise: an unacknowledged record may be present or absent. In-request retry verifies the same ID/content. Persisted attempt without decision or decision without completion remains uncertain. A new client HTTP attempt gets new IDs and cannot inherit an earlier release receipt. |
| Accepted record later unavailable/lost                                   | Treat as a durability incident; close new logs admission, preserve receipts/remaining records and investigate gaps. Never claim guaranteed delivery or silently relabel lost evidence as delivered.                                                                                                   |

At-least-once transport is acceptable; exactly-once physical storage is not assumed. Use immutable IDs plus content digest for logical deduplication across retries/replicas; keep deduplication possible throughout retained evidence, not a short vendor window. A deduplication check is not producer permission to list all evidence. No post-response memory retry worker, accepted backlog or disk spool exists in this minimum design. Any future durable queue needs separate bounded replay/dead-letter policy, stable IDs, explicit age/quota closure before loss, restart/replica recovery tests and owner approval; the earlier provisional 24-hour spool limit does not authorize one here.

Recovery requires a successful verified append/receipt probe and operator review of the incident/gaps before reopening any admission closed for a permanent fault or suspected loss. Probes use separate synthetic IDs and contain no history. Platform must designate an existing alert channel and operator query/runbook for sink failures, pending-stage gaps and quota pressure before implementation; console counters alone are neither evidence nor guaranteed alerts. There is no claim that a denied request was durably recorded when every destination failed. General API readiness/business availability stays independent of this logs-only dependency. No Phase 3 diagnostics pipeline is included.

## Retention, controls and exact decisions

Carry forward the **unapproved** Phase 1 proposal: 90 days searchable plus 275 days restricted archive, 365 days total from occurrence. Late ingestion must not extend expiry. Security/privacy owners must approve or replace these durations, the minimum retrieval capability (including whether indexed search is needed), residency, purpose, investigator access, legal holds, archive/backup/replica expiry and auditable deletion manifests. Direct object storage is viable without another search service only if its retrieval plan meets the approved requirement. Retention enforcement and hold testing are required before release; no retention job or source-history expiry is implemented here.

The producer receives append/create and minimal exact-ID receipt verification only: no general search, update, delete, bucket reconciliation or retention administration. Investigator, retention/hold operator and infrastructure administrator identities are separate. Verify encryption in transit/at rest, key ownership/rotation, credential revocation, administrator tamper limits and deletion/overwrite protection. Do not claim administrator-proof immutability without an approved threat model and verified controls.
