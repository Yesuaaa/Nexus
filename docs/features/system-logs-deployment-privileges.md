## 2. Runtime/migration separation finding

**Verified risk:** when `DATABASE_URL` is absent/empty and `DIRECT_URL` is present, both startup validation and the shared client allow runtime to use the direct credential. Either variable can also contain the same privileged login despite different URLs/ports. The shared pool is initialized once; changing environment settings is not proof that already-open sessions switched identities.

Production Compose reduces accidental fallback by requiring the runtime variable and omitting the migration variable. Other hosting is expressly documented as accepting either. No repository control verifies non-owner attributes or prevents migration credentials being injected into those hosts. Do not infer separation from URL labels, TLS, pooler ports, OS user `node`, or a username that happens to resemble `postgres`.

**Required before accepting a deployment privilege model:** identify the effective runtime session user/current role through the real connection path, verify it differs from privileged migration/owner identities, supply only the restricted runtime credential to API processes, and keep migration credentials in a separately authorized job/session. Restart/reconnect all runtime pools after an approved credential change and reverify actual session identity and business compatibility. Do not print or compare raw connection strings to produce evidence.

The fallback remains unchanged in this phase. A later separately authorized production-only fail-fast change could enforce a runtime URL requirement, but must reconcile existing direct-only hosting and tests first. Until then, release needs verified deployment secret separation plus drift/restart controls; the fallback must remain an explicit residual risk, not a presumed code-enforced boundary.

## 3. Effective privilege and direct-access assessment

### Verified locally

The existing [PostgreSQL test entry](../../apps/api/tests/support/management-history-postgres.ts) applies all migrations to a fresh network-isolated PostgreSQL 16 container, uses real LOGIN sessions, and tests the Phase 2D.1A model. Restricted runtime SELECT/INSERT succeeds, browser direct reads/writes fail, and normal runtime cannot disable/drop guards, replace their function, drop the schema or assume the owner. Over-granted non-owners still hit immutable guards for UPDATE/DELETE/TRUNCATE, including empty statements; ALWAYS guards fire in replica mode and for a BYPASSRLS principal. Rollback and multi-table TRUNCATE atomicity remain verified.

An owner or principal able to SET ROLE into the owner can disable guards. NOLOGIN on the owner and NOINHERIT on a member do not prevent that SET ROLE path. PUBLIC, column grants, inherited memberships, schema/database ownership and privileged functions must be reviewed separately. PostgreSQL exposes distinct membership, immediately usable inheritance and SET ROLE checks; they are not interchangeable. See [PostgreSQL role information](https://www.postgresql.org/docs/16/functions-info.html) and [membership options](https://www.postgresql.org/docs/16/catalog-pg-auth-members.html).

**No additional universal grants/ownership/RLS migration is justified from repository evidence alone.** The tested model denies browsers using ACLs with management RLS disabled. Whether production also needs RLS depends on effective roles, provider requirements and direct exposure. RLS does not replace DDL authority separation; owners/superusers/BYPASSRLS limitations and TRUNCATE's separate treatment matter. See [PostgreSQL row security](https://www.postgresql.org/docs/16/ddl-rowsecurity.html).

The migration itself preserves all table SELECT/INSERT grants and RLS flags. Its safe constant-error function is invoker-context with empty search path; PUBLIC function execution is revoked. Readers/writers do not need direct EXECUTE on this rejection function. A compromised INSERT-capable principal can still fabricate new history; immutable guards are neither administrator-proof evidence nor authentication of every appended row.

## 4. Sanitized operator inspection pack

The [read-only psql inspection file](../operations/system-logs-privilege-inspection.sql) is **provided for an authorized operator, not automatically executed against deployment**. It is not imported by application source, a startup hook or a migration. Its exact contents were tested in the disposable container, including as the actual restricted runtime login.

It uses a RepeatableRead READ ONLY transaction, local 10-second statement/one-second lock timeouts, catalog-only SELECTs and a final ROLLBACK. It does not query history rows, sessions, password fields, connection strings, routine bodies, view definitions, comments, subscription connection options or query text. Guard configuration and policy metadata are reduced to boolean flags; raw configuration values, policy expressions and role-named ACL text are not returned. Output identifies requested principals by aliases and unrecognized objects/principals by OID. The two allowlisted source names and expected guard names are retained. Only a small allowlist of built-in capability-role names is returned.

It reports:

- Alias resolution (including not-supplied/not-found), principal flags, current/session aliases, database/schema owners, reachable memberships with ADMIN/INHERIT/SET options, and runtime/migration identity collision.
- Effective table and column privileges through inherited and potentially assumable contexts, database/schema rights, replication-role parameter privileges, guard-function EXECUTE/ownership, raw grants represented by OIDs, and relevant default ACL metadata.
- Source existence/kind/RLS flags, expected trigger event bits/enabled-always state/function binding, and guard function invoker/empty-search-path flags.
- Policies without predicates, dependent view/materialized-view paths, callable non-system SECURITY DEFINER candidates, publications, and aggregate source-table locks.
- Version, recovery/TLS observations for the inspection connection, migration-ledger existence, and per-section totals/truncation indicators.

**Limits:** validated for PostgreSQL **16.15**, with a PostgreSQL-16 major-version gate. Another major version produces no JSON report; verification remains blocked, regardless of psql's exit code. A timeout, denied catalog permission or missing report is also blocked. The pack caps each output section at 200 items, with total/truncation metadata; this caps output, not all catalog work. Any truncated section needs a reviewed narrower follow-up, not an assumed pass.

The JSON always says `verification = operator-review-required`. It has no automated secure/approved verdict. Review context flags: a MEMBER path with neither inheritance nor SET is not the same as immediate access, and ADMIN edges can require further escalation analysis. The script does not examine routine bodies, dynamic SQL, every extension/built-in routine, schema exposure configuration, actual pooler connections, backup/restore contents or network paths. It cannot prove indirect reads absent, RLS predicates safe, the guard body unmodified, or trigger behavior solely from names/flags. Objects with multiple owners, partitions/inheritance or unexpected schema/kind require separate review. OIDs are environment-specific restricted security metadata, not portable identities.

### Optional restricted migration-ledger check

The main pack only reports whether `public._prisma_migrations` exists. An authorized operator may separately run this read-only query **after verifying the table exists and SELECT is authorized**. It intentionally excludes the ledger's error/log text and all business data:

```sql
BEGIN TRANSACTION READ ONLY;
SET LOCAL statement_timeout = '5s';
SELECT migration_name, checksum, finished_at, rolled_back_at, applied_steps_count
FROM public._prisma_migrations
WHERE migration_name IN (
  '20261115030000_management_attribution',
  '20261116130000_management_history_immutability'
)
ORDER BY migration_name;
ROLLBACK;
```

Match the checksum against the reviewed release file locally using SHA-256. Ledger absence or missing/failed rows do not establish that tables/guards are absent; manual drift is possible. Conversely, an applied ledger row is not proof the guard still exists. Inspect and reconcile both before release. The operator must also review the complete pending migration list privately, not just these two filtered rows.

## 5. Deployment compatibility and safest sequence

**Plan only; no deployment action was performed or authorized.** Installed Prisma 7's existing `migrate deploy` command applies all pending migrations, not only this file, and does not certify drift. Use the repository's pinned workflow and approved deployment job, not a newly substituted CLI or a developer terminal pointed at production. See [Prisma CLI v7 deployment semantics](https://www.prisma.io/docs/cli/v7/migrate/deploy).

1. **Preflight evidence and authority:** complete the blocked identity/grant/exposure review, identify actual PostgreSQL/pooler/provider versions, public-schema placement and existing source tables. Verify all pending migrations, checksums, function-name conflicts and ledger state. Stop on unrelated/unapproved pending changes, missing attribution foundation, alternate schemas, unsupported versions or unexplained pre-existing guards. Do not edit an applied migration to accommodate drift.
2. **Approve the identity model:** inventory all business privileges of the shared runtime and actual DDL authority of the migration principal. Define separately authorized owner/ACL/RLS changes if the inspection requires them. Verify eventual function/table owners individually; migration creation need not yield identical owners. Applying the existing guard migration is not permission to transfer ownership or revoke grants. Do not expect SET ROLE in one connection to configure another migration connection or a transaction pooler.
3. **Back up and rehearse:** owner-approved protected backup/PITR and a successful restore rehearsal in isolation, covering functions, owners, grants, triggers and ledger as well as data. Do not export raw production histories to this repository. Inventory cleanup, restore, retention, replication and administrative jobs for destructive history writes; reconcile them before deployment. ALWAYS guards intentionally reject replicated UPDATE/DELETE/TRUNCATE too.
4. **Qualify compatibility:** use a disposable target matching actual role and pooler behavior with synthetic data. Demonstrate ordinary business writes and required SELECT/INSERT, required-history failure rollback, no data loss on actor/subject deletion, direct browser denial, runtime DDL/DML denial and post-restore guard state. Current local tests do not certify hosted failover, real pooled identity or an older application rollback version.
5. **Schedule and bound locking:** plan a low-traffic/maintenance window and approved deployment-session lock/statement deadlines. CREATE TRIGGER and ENABLE ALWAYS acquire SHARE ROW EXCLUSIVE locks, conflicting with ordinary writers; the transaction retains acquired locks until completion. Different concurrent writer lock orders can delay or deadlock installation. Observe counts/waits without exporting query text; coordinate writers if needed rather than killing sessions or disabling guards ad hoc. No zero-downtime guarantee follows from a short SQL file. See [PostgreSQL locking](https://www.postgresql.org/docs/16/explicit-locking.html) and [trigger-state DDL](https://www.postgresql.org/docs/16/sql-altertable.html).
6. **Authorized execution only:** use the approved one-off migration job with separated credentials and the unchanged transaction-wrapped migration. Container startup is not a migration job. No new grant policy, blanket RLS switch or service-key exposure change may accompany it without its own review. Do not change the System Logs activation gate or unavailable navigation.
7. **Postflight and ownership acceptance:** privately verify ledger/checksum and exact trusted function/trigger definitions, enabled-always state, effective owners/memberships and direct-access denial. Reconnect approved runtime pools after any credential changes and verify real runtime identity and business health. Run behavior probes on a matching disposable environment; any permitted production smoke mutation needs separate explicit authorization. Keep the viewer disabled and record residual operator/INSERT-forgery risks.

The locks described are PostgreSQL 16 semantics, not measured target contention. Deployment timeouts and job coordination remain owner decisions requiring target evidence. The runtime image lacks CLI tooling, and repository CI has no database deployment job; the actual approved migration executor is still unresolved.

### Rollback and failure plan
