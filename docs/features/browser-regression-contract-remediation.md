# Browser regression contracts — Phase 4C.1

Developed: 2026-11-15 (Asia/Manila).

This phase establishes the complete current non-live Chromium baseline and changes only verified obsolete browser-test contracts. Production UI, navigation, routes, APIs, authorization, business workflows, mobile interaction code and all earlier uncommitted work are preserved.

The [initial baseline report](browser-regression-baseline.md) classifies every original failure. Its [449-case original manifest](../testing/phase4c1-browser-baseline.json) records every passing, failing and skipped case independently of the final results. Initial raw JSON, logs, traces and error snapshots are preserved under ignored `.ci-tools/phase4c1-browser-initial.{json,log}` and `.ci-tools/phase4c1-initial-artifacts/`.

## Initial full run and scope

A fresh `pnpm build` succeeded before the unfiltered suite ran on a dedicated local production server at port 5273. All 806 source/schema/test/documentation/reference hashes matched the starting snapshot immediately after the run. No test/source edits occurred before baseline completion.

Original full run: **449 registered, 411 passed, 33 failed, five existing live-only skips, zero blocked, zero flaky**, exit 1. Duration: 8.65 minutes. All 33 failures match the [Phase 4A backlog](superadmin-comprehensive-authorization-audit.md#full-browser-failures-and-classification); the current suite has six additional registrations/passing cases compared with that historical 443-case report. No newly failing case relative to that recorded backlog was observed. This is a working-tree comparison to historical evidence, not a claim about failures on HEAD or the date each test was introduced.

Classification: 31 confirmed obsolete expectations and two uncertain mobile interaction failures reserved for Phase 4C.2. No baseline failure was classified as an infrastructure blocker. Executed assertion/test timeouts are failures, not blocked or skipped tests. Both original and final runs retain the same test set, existing skip rules, two workers, retry policy and timeouts.

## Remaining interaction failures and unavailable checks

These original tests remain unchanged for Phase 4C.2:

- `dropdown-positioning.spec.ts`, `service pricing menus stay anchored above form controls at 390px` (390×400 viewport): the action trigger expands but `Edit` never becomes available. The baseline accessibility snapshot shows the expanded trigger and no accessible menu. Whether the cause is mounting, clipping, focus/viewport behavior or fixture interaction remains unproven. The test retains its exact menu click and popup geometry checks; no absent Edit action is excused.
- `table-interactions.spec.ts`, `workspace, team, task and deliverable tables use shared row transitions at 390px`: the Project Management card click is intercepted by the carousel before the project tables are reached. The record documents the click failure, not validated downstream mobile table behavior. Existing carousel focus/navigation may be involved, but this phase does not alter the click sequence, force it or bypass the selector.

These are reproducible interaction symptoms retained as failures, not conclusively isolated production-code root causes. No production defect was repaired or newly certified as resolved. The [Phase 4A audit](superadmin-comprehensive-authorization-audit.md#full-browser-failures-and-classification) had also reproduced both with one worker. No additional permission or HR eligibility change is justified by them.

The final full run also newly observed a failure in unchanged `administrative-requests.spec.ts:139`, `backend rejection clears request details despite a cached administrative capability`: the expected backend-denial alert was absent after the standard five-second assertion window. Its final accessibility snapshot contains only `Loading your account…`. This case passed in the initial full baseline, its source/fixture and production source are unchanged, and it is not reclassified as an obsolete expectation. Classification: **uncertain, intermittent loading/timing failure requiring investigation**; an environment/hydration delay is a possibility, not a proven cause. The denial assertion did not complete in that full run, so it is not claimed to pass there or to establish an authorization bypass. The unchanged isolated command `playwright test administrative-requests.spec.ts --grep backend.rejection.clears.request.details --repeat-each=3 --workers=1` passed all three repetitions with the same production server, fixtures, assertion window and zero retries. It does not erase the full-run failure. No timeout, retry, skip, fixture or UI change is made for this case, and no causal regression from the nine edited specs is established.

Five existing `regression-live.spec.ts` tests remain intentionally skipped because live mode is disabled: four live role-account scenarios and one deactivated-account login. They are explicitly NOT TESTED, not passing tests or new offline blockers. No unavailable live checks are counted in the non-live pass total. Native/API runner availability and final quality results are recorded separately below; raw `tsx` startup is not redefined or repaired by a browser-contract phase.
