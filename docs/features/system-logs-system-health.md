# System Health (Phase 3C)

Developed: 2026-11-16

Follow-up: [Phase 3D UI/UX refinement](system-logs-ui-refinement.md) simplifies the shared page and clarifies status presentation without changing the health contract or calculations below.

**Read-only instance-local observations for attested offline testing. Production System Logs remains disabled.** This adds the third view under `/system-logs`, following [Phase 3A](system-logs-error-foundation.md) and [Phase 3B](system-logs-error-ui.md). Activity & Audit and Errors & Exceptions retain their existing UI and response behavior. No new infrastructure, database table/migration, diagnostic action or additional job schedule is introduced.

## Reused architecture and components

The existing public readiness probe was moved unchanged into `health/database-readiness.ts` and imported by both existing public routes and the diagnostic observer. It still uses the shared Prisma client/pool, a transaction with `maxWait: 2500ms` and `timeout: 3500ms`, transaction-local `statement_timeout: 2500ms`, and `SELECT 1`. It returns a fixed result, never SQL, credential/configuration values or exception details. Existing `/api/health`, `/api/ready` and `/api/db-check` statuses, bodies and shutdown handling remain unchanged; their calls remain uncached.

Only diagnostic reads coalesce concurrent probes and reuse a result for **10 seconds after probe completion**. No health polling, background probe, extra connection pool, external HTTP request, table scan or new retry loop exists. Manual refresh gets a current observation with a clearly dated probe result; request authorization is never cached. A probe failure is cached too, preventing repeated diagnostics from hammering an unavailable dependency. Existing authentication lookups continue to use the shared pool and established bounded read behavior.

`startApi()` continues to invoke message expiry at startup and hourly, using the same purge operation, timer, failure log and shutdown cleanup. A small in-memory observer wraps its existing promise to record start/completion/result/running state, returning the original result or rethrowing the original failure. It does not start, stop, retry, cancel or await jobs during shutdown. Overlapping executions remain possible as before; status is Unknown while any execution is running. No purge result/count or business record is disclosed. Apps composed without `startApi()` (including offline browser fixtures) correctly have no observed job result.

The page extends its existing Radix `Tabs` with **System Health**. It reuses `KpiCards` (charts disabled), `Pill` and existing semantic tones, `DetailList`/`DetailItem`, `Button`, UTC formatting, `useAsyncResource` loading/error/abort behavior, the standard authenticated same-origin client, existing shell/navigation policy and EXP styling. No bespoke card/status system or new navigation route was built. Tab entry loads once; **Refresh health** and the retry button explicitly replace the snapshot. Switching tabs unmounts this view. No restart, repair, mutation, export or administrative control is present.

## Observation contract and truthful statuses

`GET /api/system-logs/health` (including implicit HEAD) is registered after the existing offline fixture gate and current-role middleware. The activation conditions and default generic 404/no-store remain intact; no environment enable flag exists. The new service-level diagnostic authorization helper extracts Phase 3A's current persisted session/account check unchanged and is reused by Error Logs. Health checks it both before the probe and immediately before disclosure, so a role change or revocation during a wait denies the response. A race after the final check remains possible; this is per-request verification, not atomic revocation.

There are no query parameters; supplied keys yield 400 after authorization. A successful observation returns HTTP 200 even when an observed component is Unavailable. Failure to obtain a permitted observation returns fixed 401/403/503/500 messages, not partial privileged data. Every response is no-store. A complete database outage can prevent current-session authentication itself; in that case **no health payload is disclosed** and the client shows component health as Unknown. Shared middleware's pre-existing unexpected-database-error response behavior is preserved.

The closed version-1 projection contains only:

| Field                                                            | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `scope: instance`, `observedAt`                                  | The API process answering this request and its current UTC observation time. No deployment-wide inference or instance hostname/PID/configuration is returned.                                                                                                                                                                                                                                                                                                                                                |
| `api.status`, `api.uptimeSeconds`                                | Healthy when the serving process responds and is not draining; Degraded when the existing shutdown flag is set. Uptime is floored `process.uptime()`, not OS uptime, availability percentage or a historical SLA. The shutdown flag is evaluated after the probe wait.                                                                                                                                                                                                                                       |
| `database.status`, `database.checkedAt`, `probeCacheSeconds: 10` | Healthy only after the existing probe succeeds, otherwise Unavailable, including absent configuration. Checked time is completion time and may precede this request because of the cache. No connection details or SQL are returned.                                                                                                                                                                                                                                                                         |
| `lastSuccessfulCheckAt`                                          | Last successful **diagnostic** readiness probe observed while not draining; null until one succeeds. Reusing a cached probe does not invent a newer success time. This is not a history of the public readiness endpoint and does not certify the job or error collection.                                                                                                                                                                                                                                   |
| `messageExpiry`                                                  | Status, running boolean, last start/completion UTC times, last result (`succeeded`, `failed`, null) and stale boolean. No execution observed, running work, or last completion older than **75 minutes** means Unknown. A fresh successful completion is Healthy; a fresh failed completion is Degraded. The 75-minute freshness bound is an observation policy for the existing hourly schedule, not a measured runtime/SLO or enforcement action. Stale last results remain visible as historical results. |
| `recentErrors`                                                   | Status and count of retained errors occurring in the last **15 minutes**, lifetime dropped/evicted counters, and the existing 1,000-record/24-hour capacity and retention. Any retained recent errors mean Degraded observations; zero or an unavailable buffer is Unknown, never proof of health. An unreadable buffer returns null counts, not invented zeros. It copies no error IDs, actor IDs, messages or stacks.                                                                                      |

No aggregate “all systems healthy” status is invented from unknown components. Status labels are text as well as color. Client parsing checks bounded values, enums, canonical UTC times and status consistency, reconstructs only approved fields, ignores arbitrary extra fields, and uses fixed local descriptions. Failed or loading refreshes hide previous component observations rather than silently showing stale Healthy cards. All four cards show Unknown when the request fails; the alert distinguishes unavailable observation, denied account and production-disabled route. The view shows observation/probe/last-success times and preserves missing job observations explicitly.

## Scope and limitations

- All observations, probe cache, last-success time, job state and error counters are in process memory. They reset on restart and are not durable history. A refresh may hit a different API replica; this feature does not discover replicas, aggregate them, establish affinity or measure external reachability.
- Recent errors summarize at most the existing 1,000 retained records. Restart loss, TTL expiry, evictions, drops and partial collector coverage limit what is known. Lifetime loss counters cannot identify which selected 15-minute events are missing. An error observation indicates a captured failure, not necessarily a current outage.
- Reading this view does not execute the expiry job. Healthy job status means a sufficiently recent observed success, not guaranteed correctness, scheduling or successful future executions. A hung job is not timed out or repaired by diagnostics.
- Timestamps/freshness use the process wall clock and assume synchronized clocks. Uptime uses Node's process uptime. These snapshots do not establish latency, saturation, load capacity, backup validity, credential/grant correctness, storage durability or a production readiness release decision.
- Authorization still depends on the application database. A failed auth store cannot be bypassed to inspect a database outage, and a cached health probe never substitutes for current-session authorization. Query transactions and final auth checks have their existing limits; the probe's configured timeouts are not a new end-to-end SLO.
