## Authorization and storage

`GET /api/service-operation-logs` requires a current active Superadmin, module access and organization-read capabilities. Other roles cannot read it. Validated filters, explicit safe projections, timestamp/ID ordering, 25-row pages and repeatable-read transactions bound reads. Backend denial hides loaded rows/details. No write/export endpoint or developer-role bypass is added.

Migration `20261117140000_service_operation_logs` adds `ServiceOperationLog` and time/outcome/request/actor/correlation indexes. Migration `20261117170000_service_operation_log_actor_name` adds the nullable, bounded actor-name snapshot without rewriting existing rows. Migration `20261117180000_service_operation_log_failure_diagnostics` adds nullable diagnostic code and safe-reason fields; legacy incidents receive an explicit read-time fallback rather than invented detail. Migration `20261117190000_service_operation_log_audit_context` adds nullable target type/name and validated JSON changes. Scalar identity snapshots have no foreign keys, so deletion cannot cascade into logs or create business deletion restrictions. Application writers append; database owners can still modify records. Deploy all pending migrations before starting this API version.

## Coverage and guarantees

- Catalog: service creation/update/status/deletion and pricing-template update/deletion. Embedded package, benefit and pricing changes are covered by the enclosing service operation.
- Requests: submission, Head acceptance, Client cancellation before acceptance, and conclusion through workspace completion.
- Workflow: every completed structured command, including requirements, consultation scheduling and rescheduling, quotations, agreement/payment reviews, reviewer assignment, staffing, activation, hold/resume, cancellation and internal-note creation. Each success records the safe fields relevant to that commandâ€”for example status transitions, counts, schedule timestamps, quotation version and amount, attachment presence, assigned reviewer names, or project staffingâ€”instead of only naming the action. Completed execution does not imply a review decision was approval. Existing action receipts prevent duplicate success logs on retries.
- New workflow uploads omit file IDs, names and content. Workload records capacity changes, staffing allocation/reassignment and removal.
- Incidents: unexpected 5xx, including 503, from catalog, request, workflow, workload and their administrative read routers. Ordinary 4xx responses are excluded.

Success logs share the business transaction. Business rollback removes logs, and log insertion failure rolls back the mutation. Actors come from authenticated context or existing authorized service arguments; name and role are read inside the transaction. New rows retain the actor's bounded display name for the 30-day log lifetime. Legacy rows resolve the current account name when possible and explicitly report that provenance; missing accounts show as unavailable, while actorless operations show as System. HTTP responses carry a generated `X-Correlation-ID`; caller actor/correlation claims are ignored. Action codes use a closed allowlist. Endpoint metadata uses static Express route templates without parameter values or query strings.

Readable messages come from closed server-side event, workflow-action and static-route catalogs. New success rows identify the affected service, request, staff member, pricing template, or project and store only allowlisted field changes as `before → after` values. The shared details drawer displays **Who**, **Affected record**, and **What changed**. Creation/deletion and workflow actions use explicit lifecycle changes when no prior or final scalar value exists. Legacy rows remain readable and state that field-level changes were not captured instead of inventing a history.

Failures identify the attempted operation and affected record, such as updating a named staff member's capacity or changing a named service's availability. Endpoint-specific enrichment records only approved attempted values and queries the rolled-back/current record for a verified prior value when available. The drawer replaces **What changed** with **What was attempted**, then shows the safe reason, diagnostic code, HTTP status, static endpoint, and correlation ID. Enrichment is best effort: a database outage can leave only the operation and diagnostic metadata. Search matches target labels, the safe message catalog, diagnostic fields and stored identifiers/metadata; it does not search private business content.

Unexpected 5xx incidents receive one stable code from a closed diagnostic taxonomy and its fixed safe reason: activity-log persistence failed, database unavailable, database timeout, database operation failed, file storage unavailable, dependency unavailable, request timeout or unexpected server error. A typed activity-log insertion failure verifies that the enclosing business transaction rolled back and is reported as `ACTIVITY_LOG_PERSISTENCE_FAILED`; it is no longer collapsed into a generic database failure. The classifier inspects only recognized error types/codes and never copies exception messages. An unknown cause remains explicit as an unexpected server error rather than guessing.

Incidents persist independently after rollback and cannot replace the original response. If database storage fails, safe structured fallback data goes to server output; database outages can leave gaps in the viewer. Raw exceptions and stacks remain server-only. Server error output now includes the same generated correlation ID, static endpoint and HTTP status shown in the portal, so developers can search one request without exposing raw diagnostics to Superadmins. No global pipeline, browser-error/crash capture or outage-independent storage is claimed.

Payloads allow only approved activity/diagnostic codes, fixed safe reasons, timestamps, bounded actor/target labels and IDs, static endpoint templates, HTTP status, generated correlation IDs, and an allowlisted maximum of 16 bounded changes. Callers choose each approved field; generic request-body or model-snapshot storage is prohibited. A workflow action code is retained only when it belongs to the existing closed action allowlist. Bodies, credentials, IPs, headers, email addresses, contact details, descriptions/goals/requirements/notes, conversation content, financial references, filenames/content, raw error messages and stacks are excluded. Workflow logs use counts, statuses and attachment-presence labels rather than copying requirement text, notes, references or files. Existing workflow summaries are never copied. Private messaging, conversation-level meetings, notification/read markers, Client Management's existing account history, and general Project Management activity are outside initial coverage.

## Retention and operations

Expiry is a rolling **30 × 24 hours**. Reads always exclude expired records. Cleanup runs at API startup and hourly, with an overlap guard, and deletes rows strictly older than the cutoff. The timer stops on shutdown; cleanup resumes at startup after downtime. Physical deletion can lag expiry by an hourly interval. Infrastructure backup retention is separate. Business, workflow and existing management history are retained independently.
