## Component reuse and behavior

The existing page now uses the shared shadcn/Radix `Tabs`, `TabsList`, `TabsTrigger` and `TabsContent` for **Activity & Audit** and **Errors & Exceptions**. Activity filters, operation investigation, details and pagination keep their existing implementation and page state. The new view reuses `FilterSelect`, `Input`, `Button`, `ResponsiveDataTable` and its row/cell/error/skeleton components, plus `SidePanel`, sections, details and footer primitives. It retains EXP colors/Inter, the current page header/shell, current route policy and active-Superadmin navigation rules. There is no new navigation destination or bespoke table/panel system.

Error filters support module (including Platform), category, severity (currently Error), exact HTTP status, and inclusive from/to UTC timestamps. Blank times use the server's last-24-hour window. Applying or refreshing replaces results and closes stale details. Error-view state resets when its tab unmounts; Activity state is retained by its existing parent. No pagination cursor or export is introduced for the bounded error buffer.

Rows show UTC time, module/category, safe code, operation and HTTP status. Details display only the returned sanitized snapshot, including safe fixed message, error/correlation IDs, verified actor ID if recorded, HTTP method/template and severity. No second detail query can accidentally hit a different replica. The panel explicitly warns its snapshot may expire or be evicted. Client parsing reconstructs the approved projection and fixed messages, discards arbitrary fields and rejects invalid metadata/IDs/enums/templates; raw server exception or API error text is never rendered.

The view always explains instance-local coverage, restart loss, separate replica buffers, 1,000-record capacity, 24-hour retention and the newest-100 response cap. It displays truncation, eviction, dropped and expired counts. Counters are since process start across that instance, not counts of missing matches for the selected filter. Matching counts describe only retained records in that instance at the read; they are not historical totals. Refreshes may reach another instance in a deployment without affinity.

Loading uses existing table skeletons. Failure hides previous records and offers the existing retry control; 404 explains the production lock, 401/403 explains denied access and other failures use a fixed retry/filter message. Empty retained results explicitly do not prove no failures occurred. A query window ending at/before the retention cutoff has a separate expired-window message: historical matches are unknown. Records that expired earlier are never reconstructed. The idle browser does not continuously expire a rendered snapshot; refresh requests a new retained view.

## API and privacy

`GET /api/system-logs/errors` (including Express implicit HEAD) is mounted **inside** the existing System Logs router, after its unchanged native-worker/fixture ownership gate and current `requireAuth`/exact-Superadmin middleware. Normal development/default/production composition returns the existing generic 404 with `Cache-Control: no-store`; there is no environment-variable bypass. The underlying service independently rechecks persisted session, expiry, current role, active and non-retired state before reading. Existing management-history adapters, records and writers are unchanged.

Allowed query keys are `moduleId`, `category`, `severity`, `status`, `from`, `to`. Unknown, repeated, structured, invalid enum/status/date or reversed-range values are rejected with 400 after authorization. Dates must be canonical UTC millisecond timestamps. HTTP statuses are integers 100–599 because an error after headers can retain a committed non-5xx status; internal records have null HTTP context. Filtering scans at most the existing 1,000 retained records **before** selecting the newest 100, so a specific older retained match is not hidden by unrelated newer records. It does not mutate domain data; TTL pruning updates only buffer bookkeeping. Existing auth session activity writes remain existing authentication behavior.

The Phase 3A envelope/projection is retained and extended with:

| Field                                                | Meaning                                                                                                                                  |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `expiredCount`                                       | Saturating process-local TTL-pruned record count; no payload retained for expired records.                                               |
| `retentionCutoff`, `windowExpired`                   | Server cutoff and whether the entire requested window is outside retention.                                                              |
| `matchedRetainedCount`, `returnedCount`, `truncated` | Matching records retained in this instance, actual returned count (max 100), and whether more retained matches were omitted by that cap. |

The original `scope: instance`, `durable: false`, `retentionHours: 24`, `capacity: 1000`, `evictedCount`, `droppedCount`, version and sanitized `events` remain. No stack, SQL, body, token, connection string, internal diagnostic code/retry flag or raw exception message is added. Error IDs and actor/correlation identifiers remain restricted operational identifiers. No new diagnostic details endpoint, raw console reader or unrestricted metadata search exists.

Current-session failures return 401/403; service authorization/storage failures return generic 503; unexpected handler failures return generic 500. Failures in the pre-existing shared authentication middleware retain its existing safe boundary behavior, including 500 for some unexpected database faults. The reader does not change business/auth response contracts to normalize those paths. No-store applies to success, disabled and error responses. A logs-only failure does not change unrelated business behavior.

## Limitations and Phase 3C prerequisites

- Storage remains non-durable and per process; no replica-wide index, archived history, complete match count beyond retained data or retained payload for expired/dropped/evicted records exists. Full-buffer counters cannot establish selected-filter history. Queries have no multi-request snapshot/pagination guarantee.
- The [Phase 2D.2A durable access-evidence provider decision](system-logs-durable-access-evidence.md), deployed database/credential protection verification, capacity qualification and a separately reviewed access/privacy/release decision remain production prerequisites. Successful local UI/API tests do not satisfy or waive them.
- Before a separately authorized Phase 3C, define its specific diagnostic scope, approved safe metrics and collection sources, current-session access design, failure semantics, sampling/capacity limits and storage expectations. Do not infer authorization for System Health, new collectors or infrastructure from this UI phase. If persistence or cross-replica history is needed, settle and authorize that architecture separately.
- Production activation remains a separate release decision. The unchanged activation lock is deliberately stronger than a UI switch or environment flag. No new diagnostic route is available in normal production composition.

**Stop after Phase 3B.** No System Health, Phase 3C implementation, infrastructure provisioning or production System Logs activation is authorized or implemented here.
