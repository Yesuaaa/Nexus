# Comprehensive Superadmin authorization audit (Phase 4A)

Audited: 2026-11-15

## Scope, baseline and conclusion

This audit evaluates the complete current working tree, including the uncommitted Phase 2A capabilities, Phase 2B registration, Phase 3A project inspection/rename, Phase 3B request/workflow/workload inspection, Phase 3C Attendance/HR administration, Phase 3D business-conversation metadata oversight/privacy validation, and the testing recovery changes. The phase reports, production controllers/services, frontend policies/actions and existing tests were reviewed together. HEAD alone is not the implementation under review.

**Overall: PARTIAL.** All five implemented modules have a Superadmin administrative entry without Employee, Staff, Department Head, Client or project membership. The new global inspection endpoints do not confer operational participation. Existing project rename and Attendance decisions retain their business checks and actual actor. However, the existing department-read exposure and read-triggered HR writes prevent a clean least-privilege result. Client creation still shares a read permission, and actor provenance is incomplete in legacy management APIs.

No production code, permissions, workflows or permanent test files were changed. A temporary offline probe reused `tests/support/pglite-app.ts` to characterize department access and was removed after execution. Only this report and its documentation index entry are lasting audit changes. Before/after source hashes exclude generated Prisma artifacts. All existing uncommitted work is retained. Diagnostics and centralized System Logs are outside scope.

Status meanings: **PASS** means supported by reviewed implementation and applicable executed tests; **FAIL** means a confirmed mismatch; **PARTIAL** means a bounded implementation or incomplete verification; **NOT TESTED** means the stated environment/path was not exercised. Passing tests are evidence of the current contracts, not proof that every existing contract meets least privilege.

## Confirmed findings and disposition

### A01 — Staff department reads expose cross-department workforce information

**Priority P1; privacy/least-privilege gap; unresolved and pre-existing.** `auth.permissions.ts:39` grants `departments:read` to every Staff account. `departments.controller.ts:28` protects employee options with that read permission; `:39` protects any department detail with the same permission. Neither passes the caller into a scope check. `departments.service.ts:77` searches the global unassigned Staff pool; `:149` loads any requested department. `departments.repository.ts:18` selects member email, contact number, position, HR status and nested account role/active/retirement state; `:112` selects assignment-candidate contact information.

A real offline API probe authenticated an ordinary Staff member assigned to department A: `GET /api/employees` returned 403, but `GET /api/departments/<B>` returned 200 and B's employee email, phone and `ON_LEAVE` status. `GET /api/departments/employee-options?search=unassigned` returned 200 with an unassigned account's phone. No Employee, Head or B assignment was required for the requester. This confirms the concern remains unresolved; hiding management pages does not enforce a backend privacy boundary. No password hash, payroll or credential exposure was found in these projections.

Recommended next implementation: identify the minimal department summary required by existing Staff callers; separate that summary from management member/account projections; authorize candidate searches with management authority or a documented operational staffing scope; apply server-side department scope and response minimization to detail reads. Preserve Superadmin/Admin organization management and legitimate Head staffing needs. Add direct API cross-department negative tests and exact response allowlists before changing access.

### A02 — Department GET can perform HR writes with read permission

**Priority P1; integrity gap; unresolved and pre-existing.** `departments.service.ts:149` calls `departmentsRepository.getDepartmentDetailsWithCleanup`. `departments.repository.ts:137–180` clears stale Head titles, clears a current Head's team and calls `syncEmployeeForUser` during detail retrieval. The controller requires only read permission. Consequently this cleanup is not limited to an authorized management mutation or to the caller's department.

The same offline probe seeded a stale Head title on a department B User and Employee. Staff in A fetched B's detail: both persisted position fields became null. An explicit `PUT /api/departments/<B>` by that Staff account returned 403. Existing `apps/api/tests/department-integrity.test.ts:89` also expects cleanup as a GET side effect, but tests it as Admin, not as a read-only Staff caller. This is a conditional write on inconsistent data, not an arbitrary write of any client-supplied field.

Recommended next implementation: make GET observational; perform necessary repairs inside an appropriately authorized existing management transaction or an explicitly controlled repair path. Preserve temporary Head restoration and team eligibility. Update the integrity tests to verify those invariants at write time, and add a read-only caller state-snapshot test proving GET makes no HR changes. Do not add a general administrative bypass.

### A03 — Client creation still uses a read permission as write authority

**Priority P2; permission-design gap; no demonstrated current-role escalation.** `clients.controller.ts:17–22` applies `clients:read` to the entire router and adds a Superadmin role check only for PATCH. POST therefore has no separate create permission. The earlier Superadmin exclusion was corrected in the existing working tree by removing the Admin-only POST gate. Current fixed mappings give `clients:read` only to Admin/Superadmin; both are intended Client creators. Staff/Client cannot create, and `clients.repository.ts:77` forces new accounts to `USER`, ignoring a submitted privileged role. Existing integration tests verify these boundaries.

Disposition: Superadmin's immediate create-access bug is resolved, while the read-versus-create concern remains unresolved. There is no currently configurable read-only role, so do not misreport a present Staff-to-Superadmin escalation. However, assigning this read permission to a future viewer would silently grant account creation. The Client page also always renders Create for authorized directory users.

Recommended next implementation: introduce an explicit Client-create permission using the existing permission maps, granting it only to today's intended creators; apply it to POST and Create controls. Preserve Admin edit/delete denial, fixed `USER` role, password validation and linked-history deletion guards. Add tests for a read-only authorization configuration without enabling arbitrary custom roles or new permission-management features.

### A04 — Actor provenance is incomplete outside the new attributed mutations

**Priority P2; traceability gap, not a demonstrated authorization bypass.** Project rename persists actual `WorkflowEvent.actorId`; Attendance approval and policy/edit auditing retain actual actors. In contrast, `users.repository.ts:26` receives target ID and hashes for password reset, and its status/create/role mutation signatures do not carry the actor. `clients.repository.ts:45` saves a Client without an actor. Employee and department controllers call profile/structure mutation services without a caller identity. These legacy paths validate authorization, but cannot consistently identify which authorized administrator performed a persisted change.

Recommended next implementation: define which existing domain mutations require durable actor provenance and carry the authenticated actor into their existing transactions; use appropriate domain history/attribution fields. Add actual-actor and spoofed-actor tests with rollback behavior. This recommendation does not authorize Diagnostics, centralized System Logs or a new generic logging feature. A new persistence design, where needed, is separate work.

### A05 — Regression coverage does not yet give a clean full-browser gate

**Priority P2; validation gap.** The expanded browser run and failure classification are recorded below. Correct obsolete expectations and fixtures only after confirming the intended current contract. Keep forbidden-content/no-API-fetch assertions and operational authorization assertions; do not change production policy to satisfy an old redirect or UI-copy expectation. Any genuine UI interaction issue needs an isolated reproduction and separate scoped fix.

## Test coverage and remaining gaps

The full API run includes `tests/features/auth/{capabilities,capabilities-integration,module-access,administrative-projects,administrative-project-management,administrative-requests,administrative-workflow,administrative-conversations,superadmin-people-hr}.test.ts`, `tests/features/workload/administrative-workload.test.ts`, `tests/features/attendance/superadmin.test.ts`, existing account/department/employee/Client/workflow/participant regressions, JWT sessions and safe field projections. All run through the real Express routers against offline PGlite, independently of frontend guards.

Coverage is insufficient in these specific areas:

- No retained regression currently rejects Staff cross-department contact/status or assignment-option exposure; existing HR tests explicitly preserve Staff department-list access. The audit probe proves current behavior but intentionally does not enshrine it as a desired regression contract.
- Existing department integrity tests assert GET cleanup rather than observational reads. They do not test absence of writes for read-only callers.
- No dedicated Client-create permission exists, so there is no meaningful retained read-only-versus-create authorization test yet.
- Existing account/Client/HR tests validate outcomes and permissions, not durable actual-actor attribution for every administrative mutation. Project and Attendance attribution are covered.
- Inactive/retired/current-role revocation is tested in shared middleware/capability/session and selected administrative paths, not exhaustively across every verb/endpoint. Concurrency, simultaneous role revocation during an in-flight write and exhaustive endpoint/role Cartesian products are not proven by this audit.
- New module registration is tested with an injected registry at service/policy level, not by modifying and deploying an actual future module. Registration cannot authorize that future module's unimplemented services.
- Most browser tests use isolated mocked API contracts; all 24 Attendance browser cases use actual Express/PGlite. There is no equivalent real-API browser fixture for every administrative module. Backend tests supply independent authorization evidence.
- Live-account tests are skipped with live mode disabled; their feature-role expectations should be reviewed before treating them as release evidence. Hosted database RLS, external object storage, realtime transport and deployment configuration are NOT TESTED.
