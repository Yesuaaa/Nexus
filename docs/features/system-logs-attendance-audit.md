# Workforce Compliance audit integration (Phase 4A)

Developed: 2026-11-16

Follow-up: [Phase 4B Project audit integration](system-logs-project-audit.md) adds a fourth source's narrow project subset; the three-source catalog and counts below describe Phase 4A's handoff.

**Read-only, metadata-only Attendance audit integration for attested offline testing. Production System Logs remains disabled.** This extends the existing Activity & Audit source/merge/detail architecture after [Phase 3D](system-logs-ui-refinement.md). Existing Attendance business logic, history triggers/writers, approvals, permissions, schema and migrations are unchanged. Errors & Exceptions and System Health retain their existing behavior. No duplicate history, storage integration or new collector is introduced.

## Inspected source and authorization

`AttendanceAudit` already persists audit row ID/time, entity identity, nullable actor ID, database action, reason, before/after snapshots and a unique per-row action UUID. Existing AFTER triggers populate it from Attendance records; the existing preservation trigger rejects ordinary UPDATE/DELETE. The original `/api/attendance/audit` reader uses Attendance management/department authorization and returns a broader source projection with current-name enrichment. This adapter does **not** call or expose that API, reuse its broader role permissions, join current people, or serialize its raw payloads.

System Logs continues to require its existing offline/native-worker/owned-fixture gate, current authenticated session and exact active, non-retired Superadmin authorization, including the independent service recheck. Historical actor identity does not authorize the current reader. Normal/default/production composition remains closed; no flag, route policy, credential or permission change was made. Deployment grants/RLS and direct database exposure are not established by this local integration.

No safe-integration blocker required schema/writer changes: source-owned row-change metadata is sufficient for this bounded slice. Richer workflow meanings, private values and logical operation correlation are deliberately not reconstructed.

## Approved projection and supported events

The adapter SELECTs only **`id`, `createdAt`, `entityType`, `entityId`, `actorId`, `action`**. It never fetches snapshots, reasons, employee/workday links, action UUIDs or current names for normalization. The closed runtime validator bounds IDs, accepts only catalogued types/actions and finite canonical source timestamps, and rejects malformed/unexpected selected fields without returning input fragments.

Source ID is the existing reserved `audit.attendance`; module is `attendance-monitoring` (**Workforce Compliance**). Event keys follow `<subject type>.<lowercase SQL action>`. The explicitly supported catalog has **20 combinations**:

| Stored entity type           | Subject/event prefix           | Supported actions                                   |
| ---------------------------- | ------------------------------ | --------------------------------------------------- |
| `AttendancePolicy`           | `attendance_policy`            | INSERT, UPDATE, DELETE                              |
| `AttendancePolicyDay`        | `attendance_policy_day`        | INSERT, UPDATE, DELETE                              |
| `AttendancePolicyAssignment` | `attendance_policy_assignment` | INSERT, UPDATE, DELETE                              |
| `AttendanceWorkday`          | `attendance_workday`           | INSERT, UPDATE only, matching its existing triggers |
| `AttendanceWorkSession`      | `attendance_work_session`      | INSERT, UPDATE, DELETE                              |
| `AttendanceBreak`            | `attendance_break`             | INSERT, UPDATE, DELETE                              |
| `AttendanceAdjustment`       | `attendance_adjustment`        | INSERT, UPDATE, DELETE                              |

For example, `attendance_adjustment.update` means a recorded database row update. It does not mean an adjustment was approved, who reviewed it, or what its values became. The normalized `succeeded` outcome refers only to the recorded committed row change, not a request/approval/business outcome. Unsupported entity/action combinations are outside this integration and excluded; no universal Attendance coverage is claimed.

Safe response fields are the source-qualified audit ID, source time (not work date/time), fixed module/category/severity, approved subject type/opaque entity ID, stored action and nullable recorded actor ID. Existing normalized compatibility containers have `details.kind: attendance`, null origin/session-revocation value, empty changed-fields/transitions and no raw snapshots. Those empty containers mean no approved value projection, not that no source field changed. The UI uses the Attendance kind to show the explicit privacy/context explanation instead of management change-value details.

Excluded: employee names, employee numbers, emails, reasons, notes, proposed/original/actual work timestamps, work dates, hours, breaks/durations, payroll-related values, adjustment decisions, approval actors, before/after JSON, raw SQL and diagnostics. Entity IDs and actor IDs remain restricted investigative identifiers, not anonymized data. Other unprojected correlation links are null; this does not assert that no such links exist in the original records.

## Attribution and grouping

Actor ID is read **as stored**, including null for unattributed changes. No current user/employee enrichment is performed. Attendance does not persist actor role-at-time, so role/evidence remain null/`not-recorded` even if today's account role is known or changes. Its unique `actionId` is generated per audit row by the trigger; it is **not** a shared management operation UUID. It is neither exposed nor repurposed as one. No timestamp/actor heuristic invents an operation, HTTP request, trace, job or workflow correlation.

Attendance `operationId` is therefore **null**. Existing management records keep their recorded non-null operation IDs and behavior. Page grouping excludes null IDs, adds `grouping.ungroupedEventCount`, and never counts all unattributed rows as one operation. The UI shows how many events lack a recorded operation, renders the missing role/operation as **Not recorded**, and omits Investigate operation for these records. Existing management operation investigations still query recorded UUIDs only; explicit Attendance-plus-operation filters are rejected rather than producing fabricated correlation.

The normalized read envelope is extended for this source without adding a persistence model. The existing route names and schema version remain; the third source/detail kind and null operation are handled together by the updated client. Older All Modules cursors bound to the former enabled-source set fail normal fingerprint validation rather than silently dropping the newly enabled source. This is offline integration, not a mixed-version production rollout.

## Filtering, pagination, details and coverage

The existing authenticated `/api/system-logs/management-history` list/detail routes are reused. Valid filters now include Attendance source/module, catalogued event/action/subject types, exact recorded actor/entity IDs, bounded UTC dates and page size. Policy-day composite identities such as `policyId:weekday` are supported without regex/SQL/free-text search. Compatible sources are selected explicitly; conflicting source/module/subject/action/event/operation combinations return the existing safe 400 behavior. All Modules includes the new limited source. No Attendance detail route, source business endpoint or new filter panel is created.

The adapter reuses shared Prisma `readTransaction`, parameterized SQL, explicit projections, the same `(createdAt DESC, source ASC, id COLLATE C DESC)` total ordering, signed filter/session/source-bound cursor, source snapshot boundary and existing 500-candidate scan cap plus one overfetch row. It participates in the existing merge before pagination; independently concatenating source pages is not used. Source-qualified IDs prevent collisions across histories. Details use the same source/range/auth/projection path.

Source faults remain independent. Attendance-only unavailability yields 503; a failed Attendance source alongside available sources yields explicit incomplete metadata and no continuation, not a falsely complete/empty history. If all requested sources fail, the existing generic 503 applies. Fetched malformed records are omitted with existing INVALID_RECORD/scan metadata. Unsupported catalog rows excluded by SQL are not counted as integrated coverage. No read repairs, backfills, attribution writes or source mutations occur; existing auth session bookkeeping remains existing behavior.

The retained Workforce Compliance origin now automatically selects a readable **Partial — attendance record changes** scope. It is not marked fully supported/compliant. Its coverage explanation lists the limited types and privacy exclusions. Source selection, optional exact event search, responsive table, audit detail SidePanel, source indicators, error/empty states and scope actions are reused. All Modules and other workspace defaults/manual overrides remain supported. The query-window hint and empty copy now refer to integrated audit records rather than only management changes.

## Remaining gaps

- This is row-change metadata only. It does not expose full Attendance audit snapshots, decisions, work values, approval history or complete Workforce Compliance coverage. New entity/action types or richer projections need explicit privacy review and authorization. It does not widen or replace the existing Attendance audit UI's own permissions.
- Missing role/operation/request correlation cannot be recovered from current account state or fabricated. Existing Attendance foreign-key restrictions and immutable guards remain unchanged; local reads do not attest deployed ownership, grants/RLS, direct REST exposure, TRUNCATE/administrator resistance or retention policies.
- Existing source histories retain their lifecycle. The date range and scan caps are query bounds, not retention enforcement or proof of physical scan/index efficiency. More enabled sources increase candidate work; no index, capacity/SLO or production performance qualification is implemented here.
- Separate source read transactions and timestamp cursors retain the documented late-commit/backdating limitations; this is not cross-request MVCC snapshot isolation or universal historical completeness.
- Durable access evidence, actual deployment/credential protection verification, capacity qualification and separate privacy/release approval remain production prerequisites. No other module or production activation is included.

**Stop strictly after Phase 4A.**
