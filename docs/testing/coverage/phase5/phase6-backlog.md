# Phase 6 — Prioritized regression backlog

## Basis and review decisions

This backlog uses [Phase 5.1](coverage-assessment.md) as its source of page coverage and original PW identity attribution. Phase 4's 292 original identities and assertions remain the preservation baseline; `NEX-###` is a separate proposed namespace for new work.

The targeted review found that several Phase 5.1 **UNVERIFIED** backend areas already have Express/PGlite regression test code. They are not new-test candidates unless the existing suite is run and shown to miss the behavior. Confirmed additions are limited to browser behavior absent from the Playwright suite, the successful account-create API path, and Project Workspace API routes with no corresponding API test found in the current test sources.

| Phase 5.1 candidate | Phase 6 decision |
| --- | --- |
| Registration validation | Add focused browser assertions for each implemented field rule and request suppression; retain existing server validation tests. |
| Account creation | Add the missing SUPERADMIN success path in browser and endpoint/persistence coverage. Existing role-policy tests and non-SUPERADMIN denials do not verify a successful `POST /api/users`. |
| Department team/member workflows | Add browser success coverage. `employee-integration.test.ts` already exercises the server-side team/member operations, so do not duplicate those API cases. |
| Populated client details | Add browser rendering/pagination coverage. `client-integration.test.ts` already seeds and verifies populated related records at the API layer. |
| Project Workspace mutations | Add browser coverage and PGlite API coverage. The targeted search found no Project Workspace controller integration tests. |
| Broad backend persistence/authentication gaps | Reuse existing PGlite/Express suites listed below before adding anything. Their presence is code evidence, not a claim that they passed in the Phase 4 Playwright run. |
| Request Inbox decline/delete success | Blocked: current backend has no routes or agreed success state. |

For browser work, keep requests mocked with deterministic state and assert user-visible results and request payloads. Do not point Playwright at a live database. The profile image API test already injects a storage fake; use that established seam rather than contacting Supabase.

## D. Suggested Phase 6 execution order

1. Run the existing isolated API regression suite first to establish backend results and avoid duplicate work.
2. Implement the account-create API success/persistence case and mocked SUPERADMIN browser journey together.
3. Add Project Workspace PGlite coverage in small route groups: lifecycle first, then plan/tasks, then deliverable access/state transitions.
4. Add mocked browser coverage for the workspace wizard, row actions, detail edits, and deliverable workflow, preserving distinct assertions for each operation.
5. Close the lower-risk browser gaps: registration field feedback, department team/member UI, and populated client details.

Keep original PW-001–PW-292 declarations and assertions unchanged. New browser tests should live in feature-owned files under `apps/web/e2e/` and use the `NEX-###` identifiers. The [Phase 4 preservation verifier](../../migrations/phase4/verification.md) reconciles an exact baseline; before adding specs, Phase 6 must define and review how new identities are recorded alongside the unchanged original baseline. This backlog does not modify that evidence or define a new verification tool.

No tests, application source, Playwright configuration, U00 files, or Phase 4 evidence were changed. Phase 6 has not started.
