## F. Display and data-source contracts

- The screen prefers the `/api/auth/profile` response and falls back to the `AccountContext` value during loading. Account context comes from `/api/auth/me`; bearer tokens are stored in `sessionStorage`, not a profile object.
- Name, email, role, contact, role permissions, account status fields, team/department and `createdAt` come from the safe `publicUser` projection. The page displays name, email, role label, contact, position fallback, department when available, and “Member since”/“Joined”.
- `getProfile` queries Employee only for a non-USER and only by the authenticated User ID. When present, the page displays employee ID, position, department, team, employment type, employment status and start date. These are read-only and explicitly marked administrator-managed.
- A specialist DTO exists only for STAFF with a linked Employee. Profile shows biography, specialties, social links and projects. It labels draft projects as private to the owner and published projects as visible to clients.
- Avatar URL is the User image path’s public URL, with STAFF Employee image URL fallback; banner uses the analogous User/Employee values. URLs are limited to safe HTTPS. Profile image changes update local Profile state; personal-name/contact saves also dispatch `nexus:account-updated`, refreshing the shared account context. The new browser test verifies the account menu reflects the new name.
- `isActive` and `accountDeletedAt` exist in the safe DTO but are not rendered as account-status controls/labels. Inactive and deleted accounts cannot load the route because authentication middleware rejects them.
- The current Profile API response does not include a password hash, refresh token, reset token or session secret. It returns only the authenticated user projection, that user’s Employee/specialist details and image URLs.

## J. Database and persistence

- `User` stores account name/contact, image/banner paths, role, active/deleted status and creation timestamp. `Employee.userId` is optional/unique; Profile loads only the Employee linked to the authenticated User.
- Personal changes update User and linked Employee name/contact inside one `$transaction`; invalid input is rejected before writes. Tests compare both records after invalid requests and verify valid read-after-write.
- Specialist data is stored on Employee (`profileBio`, image/banner fallback URLs, `profileSpecialties`) and related `SpecialistSocialLink`/`SpecialistPortfolioProject` rows. The update checks `Employee.updatedAt`, then updates Employee and replaces related rows inside one transaction. Existing tests verify a second stale write returns 409; new boundary tests verify exact maximum lengths and failed-input non-persistence.
- User and Employee profile images are stored externally; a path is saved on User and the STAFF Employee receives the public URL fallback. Project images are uploaded before their URL is attached to a portfolio project. PGlite uses an injected fake image store; no live or shared database or external storage was used.
- P17-001 reaches the `SpecialistSocialLink.url VarChar(2048)` persistence boundary after URL canonicalization. PGlite confirms the write fails with Prisma `P2000`/length mismatch and that the transaction leaves Employee and social rows unchanged.

## K. Session and security behavior

- Browser Bearer credentials live in `sessionStorage` only. Profile values are fetched from `/api/auth/profile`; shared account state comes from `/api/auth/me` and refreshes on `nexus:account-updated` after personal details save.
- Profile and image handlers derive their target from the authenticated user, not a client-provided ID. The API ignores submitted identity, role, active status, password hash, permissions, department/team and Employee IDs.
- Auth middleware rejects expired session rows and inactive/soft-deleted accounts. Existing back-end regression tests also verify role changes take effect on issued sessions.
- Profile responses contain the signed-in user’s `isActive`, `accountDeletedAt` and permission list through `publicUser`, but no credentials or another account’s data. These status fields are not editable or displayed as controls on Profile.
- Image content is bounded and magic-byte checked, but not fully decoded and no dimensions are enforced. External image hosts remain governed by the existing HTTPS/host policy.
