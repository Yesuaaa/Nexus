## 3. Source Inspection

### Route and request flow

`apps/web/src/app/(portal)/accounts/page.tsx` renders `AccountManagementPage` from `apps/web/src/features/accounts/pages/account-management-page.tsx`. The shared `PortalLayout` loads the session account and redirects a signed-in account without the required access to `/dashboard`. The page calls `accounts-api.ts`, which makes same-origin requests to `/api/users`; Next proxies API requests to the Express service.

The server path is `apps/api/src/features/users/users.controller.ts` → `users.service.ts` → `users.repository.ts` and `users.dto.ts`. Account create and role synchronization are wrapped in Prisma transactions in `createUserWithSync` and `changeUserRoleWithSync`. `users.policy.ts` selects permissions according to the actor and the current/next target role.

### Components and presentation

- Directory state, search preview, role filter, sorting, pagination, and action orchestration: `account-management-page.tsx`.
- Role selects and row action menus: `account-dropdown.tsx`, `account-row-actions.tsx`.
- Creation, password, status, and deletion confirmation UI: `create-account-dialog.tsx`, `change-password-dialog.tsx`, `account-status-dialog.tsx`, `delete-account-dialog.tsx`.
- Sort and page controls: shared `TableSortButton` and `NumberedPagination` components.
- Notifications: shared Sileo toast service; request failures also remain visible inline where implemented.

The directory shows member name and email, role, active/inactive/deleted status, department and team when present, created/deleted date, role access control, and row actions. The API DTO also supplies image URL, contact number, position, department/team identifiers, derived permissions, and head-of metadata. It does not return password hashes, access/refresh tokens, or session IDs. Email, name, contact number, and organizational relationships are still personal or account data and are rendered according to the page's role guard.

There is no account detail view and no edit form for name, email, phone, position, department, or team. The supported edit operation is role assignment. The create dialog exposes email, full name, optional phone, role, password, and confirmation; although the API accepts optional `position`, `departmentId`, and `teamId`, the current dialog does not expose them.

## 6. Authorization Matrix

| Role         | Frontend `/accounts` access                                                       | API account routes                                                            | Effective account operations                                                                                |
| ------------ | --------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `SUPERADMIN` | Allowed only with `ACCOUNTS_READ`; create/action controls use permission helpers. | Allowed by `requireRole(SUPERADMIN)`, then the route's permission middleware. | All supported operations, subject to self-change restrictions, account state, and privileged-target policy. |
| `ADMIN`      | Denied and redirected to `/dashboard`; navigation link omitted.                   | 403 at router-level role check.                                               | None.                                                                                                       |
| `STAFF`      | Denied and redirected to `/dashboard`; navigation link omitted.                   | 403 at router-level role check.                                               | None.                                                                                                       |
| `USER`       | Denied and redirected to `/dashboard`; navigation link omitted.                   | 403 at router-level role check.                                               | None.                                                                                                       |

The fixed role set is defined in the generated Prisma enum and mirrored in both auth permission modules. Only `SUPERADMIN` receives account permissions. API route permissions are: list `ACCOUNTS_READ`; create `ACCOUNTS_CREATE_BASIC` plus service `canCreateRole`; role patch `ACCOUNTS_ASSIGN_BASIC` plus `canAssignRole`; status, Trash, restore, and permanent delete `ACCOUNTS_STATUS_BASIC` plus `canChangeAccountStatus`; password reset `ACCOUNTS_RESET_PASSWORD`. The service chooses privileged permissions for `ADMIN`/`SUPERADMIN` targets or transitions.

The service rejects self role/status changes and self password reset, Trash, restore, and permanent deletion. The frontend hides self role/status/password actions. A Superadmin may assign privileged roles to another account; the implemented policy does not prohibit Superadmin-to-Superadmin assignment, but prohibits changing the actor's own role. Hidden controls are not treated as API enforcement evidence.

Evidence: `PW-001` checks a signed-in actor missing `ACCOUNTS_READ` is redirected without an account request; `PW-002` checks session lookup failure does not reveal the page; `PW-269`–`PW-272` are historical cross-role navigation cases; `role-policy.test.ts` checks middleware and fixed-role permissions; `employee-integration.test.ts` exercises actual users routes under PGlite in Phase 7.3.
