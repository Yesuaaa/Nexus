## 5. Employee Data Model and User Relationship

`Employee.userId` is nullable and unique; `User.employee` is optional, so the database relationship is one-to-one when linked and permits an unlinked Employee. `Employee.id`, `Employee.employeeId`, and `User.id` are separate identifiers. `employeeId` has a unique constraint; User email is unique. Department and team identifiers on Employee are nullable relations.

The normal create form requires employee profile fields and a password. The controller hashes the password, starts a Prisma `$transaction`, creates an active `STAFF` User with email/name/contact/position/placement, then creates the Employee using that User ID. The service also synchronizes supported profile and assignment values to the linked User. A later create/validation failure rolls back both writes. PGlite verifies the linked records and unchanged User/Employee counts after invalid or duplicate attempts.

Profile completion accepts existing non-trashed `ADMIN` or `STAFF` accounts without a password and prevents a second Employee profile. Creating a login for an existing unlinked Employee uses a separate serializable transaction. `SUPERADMIN` cannot be linked as an Employee. Account role and login status do not equal employment status.

Deactivation revokes account sessions but preserves the Employee. Archive keeps the User and Employee linked and makes the account visible in the archive query. Permanent login deletion removes the User, sets `Employee.userId` to null, and preserves Employee fields/department. A replacement Staff account can be created through the API. The list is built from visible Admin/Staff User rows, so a fully unlinked Employee row is not itself returned as a normal directory row. This is a source-observed API/list boundary; this task does not classify it as a defect or change it.

## 13. Transaction and Data Integrity Assessment

- Employee create validates the payload and password before creating writes. It hashes the password, then creates User and Employee inside one Prisma transaction. PGlite verifies the role, link, successful persistence, and no partial Employee/User rows on invalid or duplicate attempts.
- User email and Employee ID uniqueness are enforced by database constraints and mapped to conflict responses. PGlite exercises duplicate Employee ID rollback and duplicate-profile/account conflict behavior.
- Update is transactional; omitted fields are preserved, `teamId: null` is an explicit clear, and account passwords cannot be changed through Employee profile update.
- Department/team IDs are checked together. Employee/User assignment synchronization and membership projections are covered by PGlite assertions. Department-head and team-lead checks use transaction locks and reject stale/inconsistent assignments.
- Login deactivation and archive revoke sessions. Archive preserves linked Employee history; permanent account deletion leaves the Employee row unlinked and retains placement data. PGlite verifies each state and account recreation.
- PGlite is isolated in-memory evidence, not a production persistence check. Browser mocks confirm request/UI contracts only.
