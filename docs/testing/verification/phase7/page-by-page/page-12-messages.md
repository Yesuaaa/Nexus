## G. Validation audit

- Route/deep-link identifiers are accepted only when matching `[A-Za-z0-9_-]{1,80}`; malformed request IDs return to the inbox without a thread fetch in the new browser regression. API request/message/meeting/project/internal record IDs and cursors are separately validated before lookup.
- Search is limited to 200 characters and searches loaded participant, department/service/reference, and latest-preview fields; it does not claim server-wide search.
- Message text is required after trimming, at most 4,000 characters, and rejects NUL. The request API validates UUIDv4 `clientMessageId`, trims before persistence, and validates optional booking IDs. Project/internal sends also validate message text and UUIDv4 idempotency keys. Storage columns cap text at 4,000 characters.
- Enter submits; Shift+Enter and IME composition do not submit. Empty/whitespace-only sends are disabled in the UI and rejected at the API.
- Request workflow file input accepts PDF, PNG/JPEG, TXT, DOC/DOCX up to 5 MB. Preview is supported for PDF/PNG/JPEG; TXT/Word files are represented by filename. This validation applies to workflow attachment actions, not generic chat messages.
- Meeting form fields and request workflow inputs use their feature-specific schemas/controllers. No schema, validation rule, or product behavior was changed in this task.

## J. Real-time communication

Request chat uses server-side authenticated SSE. The endpoint checks bearer session/access before streaming, rechecks stream access on notifications, closes when session/role/membership is revoked, rotates streams, sends heartbeat/keepalive events, and publishes empty change notifications through private per-conversation channels with server-side listener fanout. Frontend streaming is same-origin and authenticated; visible-page refresh is a fallback, aborts/cleans up on conversation changes, merges by message ID, and reconnects with bounded backoff.

The request PGlite module exercised stream access revocation, slow validation/queue changes, and temporary stream failure/reconnect; its 11 unique leaf tests all passed. Project and internal controllers expose no SSE endpoints and use visible-page polling/refresh at roughly 15-second intervals. No live Supabase/realtime service or browser-to-real-API stream was used, so event delivery was source/isolated-API verified rather than live integration verified.

## K. Archive and history behavior

- **Project:** API explicitly supports active/archive list view. Archived project conversation history remains readable for eligible members and sending is rejected (409). Active E2E/API coverage exists.
- **Request:** current list service does not apply `view=archived`; frontend list client does not send the view; list rows are returned as `ACTIVE`; access response hard-codes `archived: false`; and the request UI exposes no delete-for-me action. `DELETE /:id` checks that attached bookings are all `CLOSED`/`CANCELLED` and records a per-user `RequestConversationDeletion`, but list/history reads do not filter those deletion records. Sending checks an active department head but does not reject a conversation solely because all attached bookings ended.
- **Contract conflict:** `docs/features/request-messaging.md` and the older Messaging regression checklist describe closed/cancelled conversations as archived/read-only and include a delete-for-me workflow. However, a current active PGlite assertion expects an all-ended request conversation to remain `ACTIVE`, `archived:false`, and sendable, and a block comment in the browser spec says legacy archive UI tests were removed because conversations remain available after completion/cancellation. These current source/test signals are inconsistent. The historical archive/delete flow is therefore an **UNRESOLVED_CONTRACT** gap; the old tests were not uncommented or restored with an assumed contract.
- The old commented archive test block in `apps/web/e2e/messages/request-conversations.spec.ts` contains USER/STAFF desktop/mobile expectations for archive/read-only/delete-for-me, retry/reload, closed deep-link, and stale inbox refresh. Equivalent active coverage exists for retaining ended-booking history and project archived history, but not request archive/delete lifecycle. No historical mapping artifact was changed.
