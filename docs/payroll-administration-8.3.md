# Payroll administration 8.3

Payroll Settings retains the Schedule, Payslips, and Disbursements sections. Readiness and Audit History are added as read-only tabs on the same route. The browser presents readiness for capabilities, while the existing payroll workflows remain responsible for validating individual runs.

Admin can edit configuration, append schedules and manage payroll subject to the existing action rules. Superadmin has Payroll read access only. Staff use authenticated ownership checks for their own published payslips and requests. Clients have no Payroll access. The access summary derives the administrative grants from the backend permission table.

The Schedule editor submits the latest schedule ID it loaded, or null if there was none. The version writer checks that value inside the established advisory lock and returns HTTP 409 if another administrator appended a schedule meanwhile. The field is optional for existing API callers. Preference writes already require the stored revision under a separate lock and preserve their existing conflict handling. The existing confirmation dialog precedes schedule creation.

## Capability readiness

GET /api/payroll/settings/readiness requires Payroll read permission. It uses narrow reads bounded to one result per dependency, except the current schedule check retrieves up to two to detect conflicting versions. Dependency failures return a generic explanation and code. An empty table proves only that the dependency can be queried. The result is not a claim about any individual run or deployment migration history.

All capability probes are read-only. They do not calculate payroll, transition approvals, publish documents, record observations, or execute payments.

## Audit visibility and reuse

GET /api/payroll/settings/audit uses the existing workforce history rows, with Payroll origin and subject scoping. Admin and Superadmin can filter configuration, compensation, period, and run events. Existing pagination returns the latest ten events per page, with a deterministic timestamp and ID order. The response exposes a safe label, current actor display name or ID fallback, role at the time, record identifier, and timestamp. The query reads the structured activity field only to allowlist existing labels for document, disbursement and reconciliation events. Raw change payloads, reasons, credentials, and employee self-service events are omitted.

Reused the Settings page, PageHeader, Tabs underline, SettingsSection, DetailList, FilterSelect, Alert, Pill, responsive table, skeletons, empty state, pagination, buttons, confirmation dialog, Switch rows, Sileo, authenticated API, async resources and date utilities. The backend reuses Prisma models, the schedule validator and Manila date helper, current preference reader, permission definitions, simulator guard, adapter flag, workforce audit rows and pagination helper. The new read service composes those sources for capability and audit views. No generic settings or audit framework was added.
