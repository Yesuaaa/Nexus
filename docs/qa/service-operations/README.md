# Service Operations QA master plan

Phase 1 reconnaissance for Converyn, 2026-11-22. Evidence comes from Nexus working tree `967b7808`, mounted Express routes, web entry points and components, Prisma schema and migrations, and the assertions and fixtures in existing tests. This is a source inventory and audit plan. Coverage below means an assertion or scenario was found in the repository. Runtime, deployment and live data behavior remain unverified in this phase.

## Cross-role workflows and persisted transitions

| Workflow                                     | Implemented transitions and audit checkpoints                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Offering → intake → routing                  | Admin or Superadmin configures a service with responsible departments and active offerings. Pricing models include fixed, starting, custom quote, recurring and hourly, with visibility controls and mutually exclusive service/package offering paths. Deactivation removes new selection. Existing references block deletion. Client submits eligible service/package/specialist choices. The API derives actor and visible pricing snapshots and deduplicates by client/submission key, rejecting changed payload reuse. A request starts `SUBMITTED` (Pending). Eligible linked Heads may see unaccepted requests. Conditional acceptance sets `UNDER_REVIEW`, stores accepting department, creates or reuses the Client/department conversation, and initializes booking workflow in the same transaction. Eligible owning Client cancellation writes `CANCELLED` before acceptance. Superadmin sees both department scopes through inspection.                                                                                                                                        |
| Consultation, requirement and quotation      | Acceptance copies commencement policy flags to `RequestWorkflow` and normally opens `CONSULTATION`. Head requests information. The Client submits it for Head approval or return (`REQUESTED → SUBMITTED → COMPLETED/REQUESTED`). Head schedules and completes/cancels structured consultations. The Client can propose a reschedule for the Head to confirm or decline. Mandatory information and required completed consultation gate quotation processing. Head prepares a fixed-price or custom quotation and creation moves it to `PENDING_INTERNAL` when internal approval is required or `SENT` otherwise. The assigned quotation approver publishes the pending version. Workflow moves from consultation or quote drafting through `QUOTATION_PENDING` where applicable to `CLIENT_APPROVAL`. New eligible versions supersede older pending/sent versions. Only the owning Client can formally accept, decline or request revisions on the latest eligible unexpired sent quote. Revision moves to `REVISION_REQUESTED`. Decline sets workflow `DECLINED` and request `CANCELLED`. |
| Quote acceptance → payment → readiness       | Formal acceptance writes the approval, approved agreement, payment checklist and one matching planned project with milestones atomically. Current acceptance satisfies the agreement. Earlier/legacy states still have document attach, sign and review handlers. Manual proof follows `PENDING → SUBMITTED → VERIFIED` or returns to `PENDING` with a reason, via the Head or assigned verifier. Sandbox checkout writes a simulated verified payment and generated receipt directly from an outstanding payment. Readiness uses a recorded approval, completed mandatory requirements and verified payment when required. Activation separately rechecks required consultation and staffing. Billing presents owned payment records with proof/receipt access scoped through workflow files.                                                                                                                                                                                                                                                                                              |
| Holds, retries and termination               | Head hold stores the previous workflow state. Resume restores it. Hold allows a limited action set. Client or Head cancellation of an eligible nonterminal workflow cancels the service request and planned project. Ended workflows restrict further structured actions. The active-project state still allows Head staffing changes when the project is eligible. Action ID, actor, payload hash and expected-version checks protect retries. Uploads have their own request/uploader/upload key and limits. Action outcomes must agree with event, recipient, version, receipt, and audit rows. Check authorization before replay after Head or reviewer changes.                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Shared conversation, meetings and calendar   | Acceptance of multiple bookings for one Client/department shares a thread and chronology with booking-specific workflow state. Authorized current participants can send and mark read. Head can edit/delete their own messages. Deleted messages use tombstones with a 30-day purge deadline. Meetings may be general or explicitly linked to one or more bookings. A reschedule request records a proposal and preserves the confirmed slot until the Head responds. Scheduled meetings may be rescheduled, completed or cancelled subject to version, state and date checks. Only an explicitly linked completed meeting can satisfy that booking's consultation gate. When all linked requests end the thread is archived, and participant deletion records a per-user hide marker. Check calendar time-zone boundaries and stale SSE/reconnect behavior.                                                                                                                                                                                                                                |
| Staffing → activation → project completion   | Head selects active department employees with active Staff accounts. Workload allocation has its own project/department/readiness checks, and writes the shared `ProjectStaff` records. Activation rechecks formal approval, matching planned project, readiness, required payment and eligible staff, then sets Project `IN_PROGRESS`, request `ACTIVATED`, and workflow `ACTIVE_PROJECT`. Workspace create/attach uses approved bookings. Reconcile Head and assigned Staff workspace access and Client project visibility. Workspace completion can set the linked service request `CONCLUDED` and write a Service Log. Eligible workspace cancellation can propagate `CANCELLED`. Verify grouped-workspace and already-terminal rules against the workspace service.                                                                                                                                                                                                                                                                                                                    |
| Workforce and lifecycle inputs               | Staff leave approval or reversal and policy effective dates flow into planning from Workforce Compliance. The workload projection summarizes seven work-date labels and approved leave minutes, treats incomplete policies and confirmed slots as unknown, and maps scheduled service commitments to the current Head. Manual capacity is scheduled minus entered time off, floored at zero. Summed in-range allocation hours and unknown hours drive utilization/status. Attendance punches, breaks and overtime totals are outside that formula. Transfers, changes in headship and account deactivation must be reflected in current access, staff eligibility, calendar attribution and notifications.                                                                                                                                                                                                                                                                                                                                                                                  |
| Client record lifecycle and operational logs | Admin/Superadmin can create Client records. Superadmin can edit and update active status, or archive an eligible unlinked Client and revoke sessions. Existing requests/projects block directory archival. Validate preserved history and status updates separately. Service Logs cover catalog/template writes, request submit/accept/pre-accept cancel/conclude, structured workflow commands and uploads, workload writes and allowlisted 5xx incidents. Success writes are transaction-coupled. Incidents can survive a rollback and fall back to safe server output. Expired rows are hidden at read time and physically pruned on startup/hourly.                                                                                                                                                                                                                                                                                                                                                                                                                                     |

Booking states and workflow/quotation states are separate. The five canonical booking labels are Pending, Under Review, Activated, Cancelled and Concluded. ## Issue tracking and scope completion

During each authorized feature audit, record findings in `docs/qa/service-operations/SO-NN-<feature>.md` and assign `SO-NN-001` style IDs. Start with the contract questions above as leads. Record the first owning scope and link downstream symptoms under the same issue when evidence shows a shared cause.

For each issue capture revision, environment and migration level. Record the actor and relationship, route, sanitized record IDs, starting state and steps. Compare the observed result with the expected contract and cite its source or product decision. Record affected roles and data, severity, status and the smallest useful regression layer. Include sanitized response excerpts, screenshots, correlation IDs and database observations as applicable. Record denials with evidence of state preservation. Keep a per-scope list of executed cases, results, unresolved decisions and handoff risks.

| Severity | Criterion                                                                                                                                                       |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Critical | Cross-client or cross-department sensitive-data exposure, unauthorized decision/payment/activation, or irrecoverable corruption in a core transaction.          |
| High     | Invalid authorization state, duplicated or lost workflow effects, material allocation/payment/date error, blocked role handoff or unreliable audit attribution. |
| Medium   | Bounded reporting, recovery, accessibility or synchronization issue with a viable workaround.                                                                   |
| Low      | Local wording or presentation discrepancy with minimal operational impact.                                                                                      |

Use **Planned**, **Confirmed**, **Needs decision**, **Ready for retest**, **Verified** and **Deferred**. Close a scope once applicable allowed/denied roles, representative invalid and terminal states, failure recovery, persisted effects and downstream contracts are accounted for. Track required follow-up with its owning scope and disposition. Phase 1 records source discrepancies and risk hypotheses without adjudicating detailed findings.
