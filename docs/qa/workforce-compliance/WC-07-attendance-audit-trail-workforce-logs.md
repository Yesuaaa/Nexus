# WC-07 · Attendance Audit Trail and Workforce Logs

**Audit date** November 21, 2026 · **Source** `305c52a5` · **Disposition** All four findings verified in isolated regressions

The original audit reproduced two high-severity and two medium-severity defects. In **WC-07-F01**, an HR transfer reopened verified correction and overtime requests, and both immutable reset rows lost the initiating actor and HTTP correlation. In **WC-07-F02**, Workforce Logs omitted a matching event after an employee rename. Both fixes were verified on November 22, 2026. The audited authorization and current-department history checks passed.

### WC-07-F01 · Verified adjustment resets lose the transfer actor and operation

1. As Staff, submit a correction for one workday. Generate overtime on a different workday by closing a session above the policy target. Verify both as the current North Head.
2. As HR, send `PUT /api/employees/:id` with the South department ID. Record the successful HTTP 200 and its server `X-Correlation-ID`.
3. Read the stored `AttendanceAudit` updates where `before.status` is `VERIFIED` and `after.status` is `PENDING`. Query the two viewer endpoints by employee or adjustment subject, then query Workforce Logs by the transfer correlation.

**Observed.** Exactly two reset rows existed. Both recorded `Database change` with null actor, actor role, operation and correlation. Audit Trail could show the reset to the receiving Head, but its actor was missing. Workforce Logs presented individual legacy-style `UPDATED` entries attributed to `No actor recorded`. The actual transfer correlation returned total 0. There was no loss of the prior Head decisions or current access. Evidence is WC-07-C04.

**Root cause.** The employee controller created a management operation from the authenticated HR account, and the HTTP logger assigned a server correlation ID. The employee placement write reached `attendance_transfer_review` before either value was installed in PostgreSQL's attendance audit context. The adjustment audit trigger read the transaction settings and used its `Database change` fallback for both resets. Workforce Logs groups by the stored operation ID, so it showed separate events and found zero results by the transfer correlation.

**Implemented fix.** The employee placement writer installs the management operation's actor, role and operation ID and the server correlation ID through the existing audit utility before changing `Employee.departmentId`. Department member assignment and removal, department deletion, and shared Employee synchronization used by department, team and account operations now propagate that context. The transfer trigger records a placement effect for authenticated moves affecting pending or verified correction and overtime review. The placement and reset effects share the operation ID used by management history. The placement effect stores only the old and new department IDs. The transaction still owns the placement, verification resets, notifications and history writes. PostgreSQL clears the settings at commit or rollback.

| Synthetic record            | Before the fix                                                                          | After the fix                                                                                                                          |
| --------------------------- | --------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Correction audit update     | `VERIFIED` → `PENDING`, reason `Database change`, actor/role/operation/correlation null | `VERIFIED` → `PENDING`, reason `Employee department placement changed`, Transfer HR / `ADMIN`, shared operation and server correlation |
| Overtime audit update       | `VERIFIED` → `PENDING`, reason `Database change`, actor/role/operation/correlation null | `VERIFIED` → `PENDING`, reason `Employee department placement changed`, Transfer HR / `ADMIN`, same operation and correlation          |
| Department placement effect | No attendance placement row                                                             | `EmployeeDepartmentPlacement`, North ID → South ID, same actor, role, operation and correlation                                        |

The operation ID matched the management history. The correlation ID matched the transfer response header, and both free-text and structured correlation searches returned one group with the placement, Correction reset and Overtime reset. The receiving Head saw Transfer HR on both resets in Attendance Audit Trail and gained verification access. The former Head received 404 for the requests and the employee's scoped audit.

### WC-07-F02 · A rename can omit a matching event in a fixed log window

1. Create 27 time-log entries `wc07-page-0` through `wc07-page-26` with descending timestamps. Give the newest entry its own employee. Link the other 26 entries to a second employee with the same current name, `Audit Paging Needle`. All entries predate page one.
2. As Superadmin, request Workforce Logs with `source=time-logs&search=Audit+Paging+Needle`. Page one returns 25 of 27. Page two with the returned `asOf` and `snapshot` returns IDs `wc07-page-25` and `wc07-page-26`.
3. As HR, change only the first employee's name to `Audit Changed Name` using the employee endpoint. Request page two again with the original tokens and filters.

**Observed.** Both tokens were identical, but total fell to 26 and page two contained only `wc07-page-26`. The reader who starts on the original page one and advances after the rename skips `wc07-page-25`. That event still matched and no source history row changed. Evidence is WC-07-C06. This is an omission from the result sequence, with the underlying history intact.

**Root cause.** The cutoff and PostgreSQL snapshot constrained the underlying audit and decision rows. Each page independently joined the current `User` and `Employee` names and reran the text predicate before counting matches and applying the page offset. A rename could therefore remove or insert a match ahead of the offset. Repeatable Read only held the names stable within a single response.

**Implemented fix.** The first text-search request collects the ordered operation group IDs from the same Repeatable Read transaction used to render the page. The API returns an opaque `snapshot` token bound to the authenticated session, filters and exclusive `asOf` cutoff. Later pages slice the saved IDs and use the original source snapshot for effects. The display projection still joins current names. Exact totals and the 25-result page size follow the saved list. Unsearched requests retain their database paging and share the same token validation. The viewer restarts from page one on refresh, filter changes, or a retry after a window error.

| Reproduction                                                                      | Before                                            | After                                                                                                                                     |
| --------------------------------------------------------------------------------- | ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Original window after HR renamed the employee on the newest event                 | Total 26. Page two contained only `wc07-page-26`. | Total 27. Page two contains `wc07-page-25` and `wc07-page-26`. Page one still includes the newest event with the employee's updated name. |
| Employee or actor renamed into the search while the original match is renamed out | Live membership was recalculated.                 | Original membership stays ordered and complete. A fresh search reflects both renames and the later commits.                               |

**Changed files.** `workforce-compliance-logs/controller.ts` validates the token and sends the authenticated session to `repository.ts`. `pagination-window.ts` owns the bounded token store. `audit-logs-page.tsx` resets the window for filter changes and recovery. `workforce-log-pagination.test.ts` covers the Express/Prisma/PGlite path. `attendance.spec.ts` and `attendance-browser-server.ts` exercise the browser against synthetic audit events and a real HR rename. The Workforce Logs contract documents the paging limits and recovery.

**Regression evidence.** The original Express/Prisma/PGlite test failed before the fix with total 26 and only `attendance:wc07-page-26` on page two. After the fix, the same test found all 27 unique IDs across both pages, including `attendance:wc07-page-25` and `attendance:wc07-page-26` on page two. It also verified renames into and out of both employee and actor searches, deterministic ID tie-breaking, late commits, current display names, refresh, empty and final pages, private-field exclusions, unchanged domain and audit records after reads, and rejection of malformed, changed, expired, cross-session and filter-mismatched tokens. Revoking the authenticated session blocked access to its existing window.

All 188 related API tests and 131 web unit tests passed. Five focused Chromium cases passed, including the real rename and both retained pages, retry after a simulated 409, fresh search, the F01 transfer, Attendance Audit Trail and scoped adjustment access. `pnpm format`, `pnpm lint`, `pnpm typecheck` and `pnpm build` exited successfully.

**Limits and concurrency.** Each process holds up to 64 windows for ten minutes. Expiry, eviction, restart, or a request served by a different process requires a fresh window. Searches over 10,000 groups require narrower filters. The offline database tests use a single pooled connection. They cover changes committed between page requests, including audit rows backdated into the original window. Overlapping transactions on independent PostgreSQL connections and routing across multiple API instances remain unverified.

### WC-07-F03 · Suspension has empty detail and manager reconciliation is described as clock-out

1. As HR, disable a Staff account with an open shift through `PATCH /api/employees/:id/account/status`. Fetch Workforce Logs using the returned correlation.
2. Reconcile as HR through `POST /api/attendance/employees/:employeeId/sessions/:sessionId/reconcile` with a confirmed end and a valid reason. Fetch the new correlation and open its detail in Workforce Logs.

**Observed.** The first operation said `Updated an attendance session for WC07 Requester.` and returned an empty changes array. The persisted session effect contained the new `suspendedAt`. Reconciliation was described as `Recorded clock-out for WC07 Requester.` despite the group having an Admin actor and originating from the manager endpoint. The confirmed end and linked overtime effects were present and the reason was appropriately excluded. Audit Trail retained the actual reason and actor. Evidence is WC-07-C05 and C09.

**Root cause.** Account deactivation updates `AttendanceWorkSession.suspendedAt` with the HR audit context already installed. The audit trigger stores that value in the session snapshot, but the Workforce Logs field list included only start and end times. Reconciliation installs the HR audit context and uses the same close routine as employee clock-out. The existing projection labeled any grouped open-to-closed session update as clock-out using its operation ID alone.

**Implemented fix.** The projection recognizes an open session gaining a suspension timestamp and exposes that value as **Suspension time**. For a session close it checks the recorded session transition, actor, role, operation and HTTP correlation. A manager close of a previously suspended session is reconciliation. A recorded employee close requires an explicitly unsuspended session. The close must preserve its original start and suspension state. Correction decisions remain primary in their groups, while break closure and automatically submitted Overtime remain linked to the reconciliation. The existing `UPDATED` action and detail components render the effects. This change requires no migration or new audit fields.

| -------------------------------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| HR suspends an open shift                                | `Updated an attendance session` with an empty change list | `Suspended an open attendance session` with **Suspension time** changing from empty to the recorded timestamp |
| HR reconciles the suspended shift                        | `Recorded clock-out` with an end time and related effects | `Reconciled a suspended attendance session` with the confirmed **End time** and related effects               |
| Staff clocks out of an unsuspended shift                 | `Recorded clock-out`                                      | `Recorded clock-out`                                                                                          |
| A historical close lacks reliable classification context | Grouped closes could appear as clock-outs                 | `Ended an attendance session`                                                                                 |

**Changed files.** `workforce-compliance-logs/projection.ts` handles classification and the approved field. `workforce-log-reconciliation.test.ts` covers the Express/Prisma/PGlite flows. `attendance.spec.ts` and `attendance-browser-server.ts` exercise the real-backend details. The Workforce Logs contract and platform reference describe the behavior.

Every effect in the reconciliation group matched the HR actor, `ADMIN` role, operation ID and response correlation. Ordinary clock-out, a correction closing a suspended session, and historical fallback retained distinct descriptions. Superadmin could read the logs. Staff, the Head, Admin and Client received 403. Pagination still uses the same ordered snapshot membership and operation grouping.
