## Confirmed findings

### WC-04-F01 · High · Missing-session corrections bypass same-workday overtime protection

**Expected.** Corrections are blocked while the workday has pending, verified or approved overtime. The existing attendance contract also defers overtime while pending corrections can change the workday. [Overtime and correction rules](../../features/attendance-interface.md#corrections-and-approvals)

**Reproduction.** In Manila, give Staff a 480-minute policy and one completed Nov 11 session from 08:00 to 18:00. Submit overtime for 16:00–18:00 and approve it as Superadmin (201 then 200). An existing-session request to shorten that session to 17:00 returns 409 with “Resolve overtime requests for this workday before correcting attendance.” A missing-session request for 06:00–08:00 on the same day returns 201 and approves with 200. The persisted workday then has two sessions and 720 worked minutes. In a fresh Nov 9 fixture with the same times, submit the missing-session request first (201 `PENDING`), then submit 16:00–18:00 overtime (also 201 `PENDING`).

**Root cause.** The correction validator checked workday overtime only when the request linked an existing session. Both overtime paths looked for corrections through `session.workdayId`, so a missing-session request could never match.

**Implemented fix.** The correction validator checks overtime for the employee's effective workday for both correction types. A linked session keeps its stored workday. A missing session uses `attendance_policy_at` through the existing policy lookup, matching the session-creation trigger. Manual and automatic overtime use one dependency query that also resolves pending or verified corrections without a linked session. Submission, Head verification and final approval use the same validators under the existing employee lock. A correction decision rechecks recorded excess so deferred automatic overtime can resume after approval or rejection. [Correction validation and review](../../../apps/api/src/features/attendance/attendance.management.ts) · [Shared overtime dependency](../../../apps/api/src/features/attendance/attendance.overtime.ts) · [Updated workflow contract](../../features/attendance-interface.md#combined-attendance-requests)

| Reproduction                                  | Before the fix                                                                                | After the fix                                                                                                                                                                                             |
| --------------------------------------------- | --------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Overtime first, then a missing correction     | Missing-session submission returned 201 for pending, verified or approved overtime.           | The second submission returns 409 in all three states. An existing-session correction is still blocked.                                                                                                   |
| Missing correction first, then overtime       | Manual overtime returned 201 while the missing-session correction was pending.                | Manual overtime returns 409 while the correction is pending or verified.                                                                                                                                  |
| Overnight clock-out with a pending correction | Clock-out recorded the shift and created pending overtime despite the correction.             | Clock-out records the shift and defers overtime. Resolving the correction generates 240 minutes after approval or 120 after rejection in the fixture. The next workday's pending correction permits both. |
| Conflict introduced after verification        | Both final approvals returned 200 when the opposing dependency was seeded after verification. | Both final approvals return 409. Deep comparisons verify that workdays, sessions and breaks, request decisions, notifications and audit records match the pre-operation snapshots.                        |

**Changed files.** `attendance.management.ts` resolves workday conflicts and rechecks recorded excess after a correction decision. `attendance.overtime.ts` shares the pending-correction lookup between manual and automatic overtime. `overtime-corrections.test.ts` exercises both operation orders through Express using seeded PGlite data. ### WC-04-F02 · High · Correction form changes or blocks daylight-saving timestamps

**Expected.** The correction form asks for actual timestamps in the device timezone and submits ordered instants. An impossible wall time needs a validation message. A repeated wall time needs a way to select the intended instant. [Correction timestamp contract](../../features/attendance-interface.md#corrections-and-approvals)

**Reproduction.** In Chromium with device timezone `America/Los_Angeles`, open Corrections → Request correction. Enter Mar 8, 2026, `02:30` through `04:00`. The clock jumps from 01:59 to 03:00 that date. Submit with a valid reason. The browser sent `10:30Z` for the nonexistent `02:30`, which is `03:30 PDT`. The API stored it with 201, HR approved it, and history reported 30 worked minutes. On Nov 1, enter `01:45` through `01:15`. The end control reported `rangeUnderflow` and invalid. The explicit API values `01:45-07:00` through `01:15-08:00` are 30 elapsed minutes and returned 201.

**Root cause.** The dialog converted local strings with `new Date()`, which normalizes a skipped time and defaults to the earlier instant for a repeated time. The clock-out field passed the clock-in wall time as its native and picker minimum. That comparison blocked `01:45 → 01:15` before the form could evaluate the offsets. The form also reconstructed existing timestamps from minute-only prefills, losing the recorded occurrence and any seconds.

**Implemented fix.** The attendance timestamp helper checks which device-zone instants round-trip to the entered time. The dialog uses the existing alert for gaps and the existing select for UTC offsets when a time has multiple occurrences. It compares the chosen instants before submitting. Existing-session prefills retain their original offset and exact instant until edited. The shared date input still supplies the calendar and native required-field handling. The API and attendance policy still validate and attribute the submitted instants. [Correction dialog](../../../apps/web/src/features/attendance/components/adjustment-dialog.tsx) · [Timestamp helper](../../../apps/web/src/features/attendance/model/attendance.ts) · [Updated timestamp contract](../../features/attendance-interface.md#corrections-and-approvals)

A direct API request with the intended offsets returned 201. | Missing offsets and a reversed instant pair show errors. Selecting `UTC-07:00` then `UTC-08:00` sends and stores `08:45Z → 09:15Z`. Staged approval produces 30 worked minutes against the 480-minute policy. |

The POST, approved session and reported total preserve the full `09:25:12.345Z → 09:40:12.345Z` interval.                                     |

### WC-04-F03 · Medium · Head changes leave pending corrections without a notice for the new reviewer

**Expected.** A pending correction follows the current independent Head or HR fallback in both review access and notification routing. [Master plan workflow and notification rules](README.md#implemented-transitions-and-workflow-checks-to-plan) · [Existing stage routing](../../../apps/api/src/features/attendance/attendance.overtime.ts#L23)

**Reproduction.** As Staff, submit Nov 10 09:00–12:00 Manila in a department with an eligible Head. Submission returns 201 and the original Head inbox contains `ATTENDANCE_CORRECTION_PENDING`. As HR use `PUT /api/departments/:id` to replace the Head (200). The replacement's correction detail returns 200 with `verify: true`, but their inbox contains no notice for the request. Remove the Head through the same API (200). HR detail returns 200 with `approve: true`, but the HR inbox still has no notice. The former Head's detail and inbox no longer expose the request. The transfer control case did generate a receiving-Head notice.

**Root cause.** Queue and inbox reads evaluate current authority. Submission, review and employee transfers wrote notifications, while ordinary Head changes, temporary leadership and Head account status changes left pending corrections without a row for the new reviewer.

**Implemented fix.** Correction submission, leadership changes and employee transfers use one pending-correction delivery function. The Department, Employee and Account lifecycle hooks run it alongside the existing WC-03 leave routing in the authority-change transaction. Correction submission acquires the department lock before the employee and rechecks placement before writing. The existing recipient, adjustment and stage key preserves identities and read timestamps when a reviewer returns during the same pending stage. A transfer that resets verification retains the established renewal for a new review cycle. The migration fills prior notice gaps for current reviewers. Existing inbox scope governs list and mark-read access. [Delivery calls](../../../apps/api/src/features/attendance/attendance.correction-notifications.ts) · [Migration](../../../apps/api/prisma/migrations/20261121190000_correction_pending_notifications/migration.sql) · [Inbox scope](../../../apps/api/src/features/request-workflow/workflow.notifications.ts#L48)
