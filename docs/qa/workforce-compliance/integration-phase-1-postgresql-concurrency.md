# Workforce Compliance Integration QA · Phase 1

**November 22, 2026 · Source `b4ba21e2e983b7f0a1be32b53bb641942619ea8c` · PostgreSQL 16.15 · Two confirmed defects**

The harness read `current_setting('transaction_isolation')` through Prisma for all three configured levels and observed `read committed`, `repeatable read`, and `serializable`. The server default was `read committed`. The reviewed workflow code uses row locks and database constraints. Advisory locks were introduced only as disposable QA barriers. At `ReadCommitted`, statements can see a concurrent transaction that committed before the statement began. A `Serializable` transaction keeps its earlier snapshot, including after a wait on a row lock. [PostgreSQL 16 isolation](https://www.postgresql.org/docs/16/transaction-iso.html) · [PostgreSQL 16 explicit locking](https://www.postgresql.org/docs/16/explicit-locking.html)

- **Deterministic write ordering.** The control connection held a `FOR UPDATE` lock on the fixture Employee. After the first HTTP transaction appeared in `pg_stat_activity`, the second HTTP transaction started. A separate observer checked both PIDs and their `pg_blocking_pids()` before releasing the control lock. In the representative deactivation run API PID `122` waited behind control PID `120` and API PID `123` waited behind PID `122` on the same Employee lock. A disposable row trigger and advisory lock paused the other scenarios precisely at a history insert, notice insert, or Department update. The harness verified that the competing request either blocked at the expected lock or completed while the first transaction was still open. Reverse-order controls used fresh fixture rows.
- **Persisted-state checks.** The harness queried workdays, sessions and breaks, requests, saved leave days and decisions, recipient rows, account and login state, and management and attendance history. Successful audit checks matched the server's `X-Correlation-ID`, authenticated actor/role, operation ID, source effects, and writer transaction. Rejected or rolled-back writes had no attendance audit rows under their correlation. Scoped detail, inbox and logs requests checked authority independently of notice rows.
- **Timing-dependent probe.** Eight fresh Employee Directory deactivation/clock-in pairs ran concurrently without database gates, alternating request dispatch order. All eight returned `201` for clock-in and `204` for deactivation and persisted an unsuspended open shift for an inactive account. This small probe reproduces WC-I1-F01 under ordinary overlap. It does not estimate a production failure rate.

## Confirmed findings

### WC-I1-F01 · High · Verified · Employee Directory deactivation could strand an open shift

1. On the original source, seed an active, linked Staff employee with an effective policy, a valid Bearer session and no attendance session. Use an HR/Admin account for the Employee Directory call.
2. Hold the Employee row in a separate SQL transaction. Send Staff `POST /api/attendance/me/clock-in` with `{}` and observe its `FOR UPDATE` wait. Then send `PATCH /api/employees/<employeeId>/account/status` with `{ "isActive": false }` and confirm the second API backend queued behind the first. Release the control lock.
3. Observe `201` for clock-in and `204` for deactivation. Query `User`, `Session`, `AttendanceWorkSession`, `AccountManagementChange`, and `AttendanceAudit` independently. The User is inactive, there are zero login sessions and one status management row, but the sole shift has both `endedAt` and `suspendedAt` null. There is no suspension audit with the disable correlation.
4. Send `POST /api/attendance/employees/<employeeId>/sessions/<sessionId>/reconcile` as HR with a valid end after clock-in and an explanatory note. It returns `409` with `Only an open suspended shift can be reconciled`. The old Staff token returns `401` on a new call. A fresh, repeated Employee Directory disable on the inactive synthetic account evaluated the now-visible shift, suspended it with attributed audit and allowed HR reconciliation to return `200`.

In the controlled main run, clock-in correlation `7da17fb4-38b6-42d1-8767-3a05471569d3`, deactivation correlation `1ac248f3-9f12-426d-b27e-d9a70dfa05d1`, and reconciliation correlation `6f9d52bd-9852-4366-9406-438b9cfcee37` matched session `cmwr4zdwj011qx4vaf4opaipe`. The reverse order and the Account Management comparison behaved as described in the matrix.

Employee Directory reads the linked account and establishes its `Serializable` snapshot before waiting for the Employee lock. Clock-in locks the same Employee without updating its row, then inserts a session. The queued deactivation can lock the unchanged Employee and update the User successfully, while its older snapshot cannot see the newly inserted shift in the later suspension statement. Revocation and management history commit with that incomplete business outcome. In the clock-out-first control the session existed in the snapshot and was updated by the other transaction. PostgreSQL instead rejected the suspension update with `could not serialize access due to concurrent update` and the route returned `409`. [Employee Directory transaction](../../../apps/api/src/features/employees/employees.service.ts#L936) · [Clock-in locking](../../../apps/api/src/features/attendance/attendance.service.ts#L37) · [Session suspension and revocation](../../../apps/api/src/features/users/account-lifecycle.ts#L99)

#### Implemented transaction strategy

Employee Directory deactivation now uses explicit `ReadCommitted`, matching Account Management's server-default isolation. It keeps the order of headed Department when applicable, Employee, then User. The linked Employee must still match the Directory lookup after locking. The conditional User update revalidates role, active state and retirement. If an account-only operation finds a newly linked profile after locking User, it rolls back with `409` so a retry can acquire the Employee lock first. The suspension statement sees shifts committed before the Employee lock was acquired. Suspension, login and refresh-token revocation, any Head fallback notices, and management history commit together. The suspension history and management row share the authenticated actor, role and operation ID. Attendance history also records the server-issued HTTP correlation. Directory activation retains its prior isolation.

### WC-I1-F02 · Medium · Verified · Overtime could miss the replacement Head's notice

#### Pre-fix reproduction and root cause

1. Seed an eligible active Head and replacement in the same department. For explicit overtime, create a closed 10-hour shift on a 480-minute policy day without generating automatic overtime and use the last two hours for the request. For automatic overtime, start an open shift and use the API clock to end it after ten hours.
2. In the disposable database, add a `BEFORE INSERT` trigger on `WorkflowNotification`, matching `ATTENDANCE_OVERTIME_PENDING` for the former Head. Have it call `pg_advisory_xact_lock(760017)`. Hold `pg_advisory_lock(760017)` in a separate control session. Start `POST /api/attendance/adjustments` with type `OVERTIME`, a fresh request key, start/end instants and a reason, or start `POST /api/attendance/me/clock-out` with the active session ID. Confirm the API backend waits in `attendance_notify_pending_adjustments` after selecting the former Head.
3. As HR, send `PUT /api/departments/<departmentId>` with `{ "headId": "<replacementId>" }`. It returns `200` while the overtime request is still uncommitted. Release the advisory lock. The overtime write returns `201` for explicit submission or `200` for clock-out.
4. Query `Department`, `AttendanceAdjustment`, `WorkflowNotification` and `AttendanceAudit`. The replacement is current, the request is `PENDING` with attributed audit, the former Head's pending notice exists, and the replacement's notice is absent. The former Head's inbox hides the stored notice and detail returns `404`. The replacement's inbox is empty for that request, but detail returns `200` and grants verification. Replaying the exact explicit submission key returns the same adjustment and still leaves the new Head without a notice.

In the alternate schedule, the Department update waited at a disposable `AFTER UPDATE` trigger before its pending-notice scan. The overtime writer committed first and the resumed replacement transaction then created the replacement Head's notice. The failing order reproduced twice for both overtime sources. The second run's explicit submission/replacement traces were `ac306876-7bce-4087-a0e3-27323858c80b` and `09c1a1dc-d350-43ff-ac68-194f10c7e748`. Automatic clock-out/replacement traces were `f7260705-f7c3-4d58-a4b9-1f5289c64a67` and `4a542afb-d082-4d7b-8d35-7bd708bc20d3`.

Explicit submission, clock-out, and reconciliation held Employee and User locks without sharing the Department lock used by Head replacement. The replacement scan could run while a new request was invisible and the outgoing notice statement had already chosen its recipient. The retained regression reproduced the missing notice on all three paths. With the Department update paused before its scan, all three producers could also finish ahead of it with a former-Head notice. The resumed replacement then delivered the current-Head notice. Correction approval already held the Department lock and passed both schedules before the fix. [Adjustment submission and review](../../../apps/api/src/features/attendance/attendance.management.ts) · [Automatic overtime](../../../apps/api/src/features/attendance/attendance.overtime.ts) · [Pending-notice SQL](../../../apps/api/prisma/migrations/20261121200000_overtime_pending_notifications/migration.sql) · [WC-05 sequential verification](WC-05-overtime-management.md#wc-05-f02--medium--verified--pending-overtime-loses-notice-delivery-when-department-head-authority-changes)

#### Implemented transaction strategy

- Explicit submission reuses the Correction placement check. Clock-out uses the same check. Reconciliation looks up and locks the subject's Department before locking Employee and reviewer User. In each path the Department `FOR SHARE` comes before Employee and User, and the transaction validates current placement before doing any business write. A transfer that changes placement while the producer waits results in `409`. A fresh request can acquire the receiving Department's lock. Correction approval continues to share the Department before locking Employee, reviewer User, and the adjustment. [Attendance service](../../../apps/api/src/features/attendance/attendance.service.ts) · [Adjustment service](../../../apps/api/src/features/attendance/attendance.management.ts)
- Each producer uses `ReadCommitted`. The pending-notice SQL evaluates current Head eligibility and recipient scope under the Department lock. Head replacement's existing Department `FOR UPDATE` covers the leadership update and pending-request scan. The producer commits first and the scan sees the request, or the leadership change commits first and the producer routes directly to the current eligible reviewer. The write paths keep request, notices, audit, and any punch, break, or correction changes in their original transaction. [Department update](../../../apps/api/src/features/departments/departments.repository.ts#L353) · [Notice routing](../../../apps/api/src/features/attendance/attendance.pending-notifications.ts)
- The Department lock is acquired at the entry points that can create overtime, before the existing Employee and User locks. The shared automatic allocation helper never takes a late Department lock. Ordinary Employee `PUT` transfer still waits on Employee and routes existing pending requests in its placement trigger. Current-Head, fallback, self-review, unique recipient, and read-state rules continue to use the existing SQL and authorization checks. [Row locks](../../../apps/api/src/shared/db/locks.ts) · [Placement trigger](../../../apps/api/prisma/migrations/20261122130000_attendance_transfer_attribution/migration.sql)

Changed files include [`attendance.service.ts`](../../../apps/api/src/features/attendance/attendance.service.ts) for the shared placement check, clock-out and reconciliation; [`attendance.management.ts`](../../../apps/api/src/features/attendance/attendance.management.ts) for submission and the Correction approval lock contract; [`overtime-routing.postgres.ts`](../../../apps/api/tests/features/attendance/overtime-routing.postgres.ts) for the retained test; and the [Attendance API](../../features/attendance-backend.md) and [workflow contracts](../../features/attendance-interface.md). This report records the status and evidence.
