### WC-03-F01 · Critical · Decision replay disclosed private information after department access changed

**Severity.** The master plan classifies cross-scope disclosure as Critical. The prior QA draft recorded that a former Head received current private leave information after losing department access.

**Root cause.** An existing decision record established that an action had been committed by the caller. The replay path validated the account and action type, then returned the current request without checking the caller's current record visibility.

**Fix.** The replay query now applies the current leave read scope and requester access before serializing a response. It uses the same scope rules as leave detail and honors Superadmin's organization-wide read scope on replay. A caller outside the request scope receives the generic 404 response. Existing session revocation still returns 401. An authorized exact retry returns the current request without adding a decision or sending a notification. Existing actions, detail routing, and notification rules retain their behavior.

**Changed files.** The leave service now checks visibility in the replay transaction. The existing PGlite-backed leave suite now checks department transfer, replacement of a Head within the same department, account revocation, and authorized exact retries. This report records the resolution. **Verification on 2026-11-21.** The isolated Express and migrated PGlite regressions passed. Former Heads received a generic 404 after both department transfer and same-department Head replacement. The deactivated account received 401. An authorized exact retry matched the original response before subsequent changes. The receiving Head's retry after approval matched the current detail response, and Superadmin's retry matched its approval response. Before-and-after comparisons preserved the full request, policy-day snapshots, decision records that back the audit trail, and notification records. ### WC-03-F02 · High · Final approval accepts a disabled requester login

1. As linked active Staff, submit December 7, 2026 leave and obtain Head verification. Keep the Employee's employment status `ACTIVE`.
2. Use the existing Superadmin account-status endpoint to deactivate the requester. The previous bearer now returns 401.
3. Approve the verified request as HR using the current version.

**Pre-fix reproduction on 2026-11-21.** The isolated API test received 401 for the disabled Staff session and confirmed that the linked employment record remained `ACTIVE`. HR received 200 with `APPROVED` v3 where the test expected 409. A second fixture reached the same incorrect approval after unlinking the original requester. Approved leave is the source of derived attendance and scheduling coverage.

**Root cause.** Final approval checked `Employee.status`, and the decision transaction protected the reviewer account. Approval had no check for the requesting account's current status, role or link to the employee.

**Implemented fix.** Final approval shares a lock on the original requester account alongside the reviewer account after locking the employee. Before recording the decision, it requires the original account to be enabled, outside Trash, currently linked to the request's employee, and eligible as Staff or Admin. A failed check returns 409 and leaves the request available for authorized review. Restoring an account from Trash leaves it inactive. Reactivating the original linked account allows approval if the other existing checks pass. A later account disable preserves already-approved leave. ### WC-03-F03 · High · Unrelated open shift blocks future leave approval

1. Under a Manila policy, clock the Staff employee in on December 7, 2026 at 09:00 local. Submit separate whole-day requests for December 7 and December 10.
2. At 10:00 local with the December 7 shift still open, have Superadmin approve the December 10 request on the valid direct decision path. Use December 7 approval as the conflicting control.
3. Clock out and retry the December 10 approval.

**Pre-fix reproduction on 2026-11-21.** With the December 7 Manila shift still open at 10:00 local, both the December 7 control and December 10 approval returned 409. The future request returned “Close active attendance sessions before approving leave.” The earlier QA run recorded 200 for December 10 after clock-out. The isolated pre-fix run also returned 409 for active and suspended New York shifts whose elapsed interval ended exactly at the start of the leave date.

**Root cause.** A blanket guard rejected any session with a missing `endedAt` before evaluating its attributed workday or its overlap with the requested dates.

**Implemented fix.** Approval checks the session's attributed workday and its elapsed interval against leave days with positive required minutes. Closed sessions use their stored end. Active sessions use the approval clock. A suspended open session uses its frozen elapsed time through `suspendedAt`, capped by the approval clock. Interval ends are exclusive and use each leave day's policy timezone. ### WC-03-F04 · Medium · Head changes put fallback decisions and HR visibility out of sync

1. Submit December 2 leave while the requester reports to a different, eligible Head. Before verification, appoint the requester as Head of that same department and keep the request unchanged.
2. Read HR's organization list, overview, inbox and detail. Compare the owner's fallback flag and attempt the normal HR decision with the current version.
3. For the reverse control, submit a separate request in a headless department, then appoint an eligible non-self Head before HR decides.

**Expected.** Current Head eligibility and self-review determine the actionable queue and notices. HR should be able to find and decide an eligible fallback request without already knowing its ID. **Observed.** After self-Head appointment, the owner's request reported fallback true and denied self-verification (403). HR's list and Submitted overview entry were absent, detail returned 404 and no HR notice appeared, but the current-version HR approval returned 200. In the reverse direction, the earlier fallback notice and detail remained visible to HR (200), approval capability was false and the mutation returned 403. The newly assigned Head could read the request.

**Root cause.** HR's list, detail, overview and inbox used a stored submission route as a fallback signal and omitted the self-Head case. Decisions used the current Head. The inbox had no delivery step for reviewers who gained authority after the submission.

An HR fallback submission notice is visible only during the eligible pending stage. Explicit Head changes, temporary handoff and restoration, and Head login status changes deliver neutral notices to newly eligible reviewers in the same transaction. The existing recipient, request, stage and version key deduplicates notices and preserves prior read timestamps. Original routing snapshots, recorded verification, and receiving-Head re-verification rules are preserved. ### WC-03-F06 · Medium · Decision replay ignores changed note and version

1. As authorized Head, verify a submitted request using a fresh action ID, expected version 1, and “Original verification note.” Immediately repeat exactly.
2. Reuse the ID for verification with a different valid note, then with expected version 99. Use the same ID for rejection as a control.

**Expected.** An exact retry returns the committed decision. Changed payload reuse returns conflict and retains original history. **Observed.** Exact replay correctly returned 200. Both changed verification bodies also returned 200 while the persisted decision still contained the original note. Reusing the ID with a different action returned 409. A reviewer can get a success response for a note the server never recorded.

**Root cause and fix.** The receipt lookup identified the original decision by request, actor, and action ID. Replay checked the recorded action alone. Each decision increments the request version once, so the original expected version is the receipt's stored version minus one. ### WC-03-F07 · Medium · Stale browser action displays a conflict but keeps the obsolete decision controls

1. Submit and verify a request. Open the HR Approve request panel against the verified version.
2. In another authorized session, have Superadmin reject the request. Submit the stale HR approval.
