## Confirmed findings

### WC-05-F01 · High · Verified · Corrected excess can remain unrequested after prior rejection

**Expected.** An approved correction rechecks newly recorded excess and generates an overtime request for new eligible minutes. Previously rejected time is excluded from automatic resubmission. [Overtime and correction contract](../../features/attendance-interface.md#combined-attendance-requests)

**Reproduction before the fix.** Give Staff a Manila policy with a 480-minute target. Clock 08:00–18:00 on Nov 12. Clock-out returns 200 and creates one 120-minute request for 16:00–18:00. As Head, reject it with 200. Submit a linked correction to change the start to 07:00 (201), then have the Head verify and HR approve (200 each). Staff and scoped HR history report 660 worked, 480 required and 180 excess minutes on Nov 12. The first automated run found zero pending overtime rows where it expected one. In the original audit, an equivalent fixture accepted a manual 15:00–16:00 claim for 60 minutes with 201.

**Cause.** `submitRecordedOvertime` correctly deducted prior request minutes from the daily budget, then selected a single interval back from the session end. Its 17:00–18:00 candidate intersected the rejected request and stopped generation. The valid 15:00–16:00 interval was never considered. Correction review already invoked automatic generation on the affected workday. [Automatic allocation](../../../apps/api/src/features/attendance/attendance.overtime.ts) · [Correction finalization](../../../apps/api/src/features/attendance/attendance.management.ts)

**Implemented fix.** Automatic generation uses the recorded workday's target and elapsed worked time across earlier sessions to find when the current session becomes eligible. It excludes unpaid breaks from the minute calculation and subtracts previously requested ranges from the candidate interval. Each remaining window can generate a separate request, starting with the latest window, within the whole-minute workday budget after recorded requests are deducted. A historical interval on a different workday blocks overlap without consuming this workday's budget. Approved-leave checks, request keys, notifications and audit writes use the existing attendance transaction. Correction finalization still calls the same generator and retains the WC-04-F01 workday conflict guards. [Updated workflow contract](../../features/attendance-interface.md#combined-attendance-requests)

### WC-05-F02 · Medium · Verified · Pending overtime loses notice delivery when Department Head authority changes

**Expected.** The eligible current Head or HR fallback can discover pending overtime through the queue and inbox. The inbox and mark-read routes enforce current source scope. [Review and notification methodology](README.md#implemented-transitions-and-workflow-checks-to-plan)

**Reproduction before the fix.** Submit 120 minutes as Staff in a department with an eligible Head (201). The original Head receives `ATTENDANCE_OVERTIME_PENDING`. Replace the Head using `PUT /api/departments/:id` (200). The new Head's queue and detail return 200 and show `verify: true`. Their inbox returns 200 with zero matching notices. The former Head's detail and mark-read return 404. Disable the replacement via `PATCH /api/users/:id/status` (200). Their old bearer returns 401. HR's queue and detail return 200 and show `approve: true`. The HR inbox returns 200 with zero matching notices. The pre-fix API run reproduced both missing notices and showed that a pending transfer reset the original reviewer's read timestamp on return.

**Cause.** Overtime wrote pending notices at creation and on transfer. The lifecycle hooks for same-department changes refreshed only Corrections and Leave. The current source scope hid the former reviewer's notice, and the new reviewer had no recipient row. The old transfer trigger also renewed every overtime pending notice, including when the request remained in its original review stage. The notification uniqueness key preserves the existing row, summary, and timestamps throughout one pending stage. When a transfer reopens a verified request, the trigger renews receiving reviewers' pending notices using the same notice IDs. The migration adds missing current-reviewer notices for pre-existing pending overtime and preserves historical notices, decisions, and audit rows. Existing queue, detail, overview, decisions, and inbox authorization continue to enforce current scope. ### WC-05-F03 · Medium · Verified · A losing browser review remains actionable after HTTP 409

**Expected.** A conflicting terminal decision should refresh request status and capabilities so the reviewer sees the saved decision and can stop retrying the stale action. The API correctly rejects a second terminal action. [Review handler](../../../apps/api/src/features/attendance/attendance.management.ts) · [Adjacent Leave conflict coverage](../../../apps/web/e2e/attendance.spec.ts)

**Reproduction before the fix.** Generate and verify a 120-minute request. In Chromium, open HR's **Approve overtime** panel and enter a note. Reject the same request as Superadmin (200 `REJECTED`). HR's detail endpoint now returns `REJECTED` with all review capabilities false. HR clicks **Confirm decision** and receives `409 {"error":"This request has already been reviewed"}`. The panel displays the error alongside `Verified — awaiting HR` and keeps **Confirm decision** enabled. The original audit got the same 409 on a second click. The stored row remained `REJECTED`. A fresh pre-fix Playwright run performed both decisions in separate authenticated browser contexts and failed at the expected read-only detail assertion after the real 409.

**Cause.** `submitReview` retries the list after success. The failure path only sets an error string. The open panel and `reviewAllowed` continue to use the cached verified row and capabilities. [Web review handler](../../../apps/web/src/features/attendance/pages/attendance-adjustments-page.tsx)

**Implemented fix.** The shared attendance page takes the recovery path only for overtime and only for authorization errors or the API's terminal-state, placement, and verification-required conflicts. It preserves the failed review response, reads the selected request again, and reloads the current scope, search, page, and filters. The panel uses the refreshed detail and clears the abandoned decision. Queue actions come from the refreshed list. Authorization errors discard the cached panel and affected row while detail access is rechecked. A failed detail read leaves the panel closed with the original error on the page. Input validation stays in the review form and keeps the draft editable. [Attendance page](../../../apps/web/src/features/attendance/pages/attendance-adjustments-page.tsx) · [Workflow contract](../../features/attendance-interface.md#combined-attendance-requests)

**Changed files.** `attendance-adjustments-page.tsx` implements recovery with the existing attendance API client, scoped list loader, and error alert. `attendance.spec.ts` exercises the losing reviewer and the winning Superadmin in separate browser contexts. The Attendance workflow contract and this report record the behavior. [Real-backend regression](../../../apps/web/e2e/attendance.spec.ts)
