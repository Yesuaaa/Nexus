### WC-I2-F01 · Medium · Legacy submitted Leave missed the current reviewer’s notice

Before `20261121140000_leave_verification_notices`, a submitted request could already have a notice for its then-current Head while historical leadership or account-status changes left the request without a notice for the successor. The current API correctly computes the reviewer from the current assignment and eligible Head. The Leave verification migration adds the notice version and replaces the unique index. The later migration backfills target Corrections and Overtime. Existing submitted Leave rows therefore keep the delivery gap after migration. #### Forward fix and PostgreSQL retest

The new migration contains one transactional insert with the same recipient criteria as `notifySubmittedLeave` when rerouting after a Head change. It uses the employee’s current department and its active, non-archived Staff Head. It excludes both the requester and the employee’s linked account from review. If there is no eligible Head, it selects active, non-archived Admins with the same exclusions. The insert uses the existing neutral summary and version `0` for `LEAVE_SUBMITTED` notices. A conflict on `(userId, leaveRequestId, type, leaveVersion)` leaves the entire original row intact. Historical migrations and the live Leave lifecycle were preserved.
