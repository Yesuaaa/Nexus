## Confirmed findings

### WC-02-F01 · High · Verified · Explicit workday selection bypasses the policy handoff

**Reproduction.** Assign one synthetic active Staff employee an eight-hour UTC policy up to December 11, 2026 (exclusive), and an eight-hour Asia/Manila policy starting December 11. The switch is December 10 at `16:00Z`. Under the controlled clock, clock in at `14:00Z` and retain that workday ID, then clock out at `15:00Z`. At `16:00Z`, read `GET /me/current`. Then send `POST /me/clock-in` with the earlier workday ID. The previous session both started and ended on December 10 in UTC, so this is an ordinary split-shift fixture with no earlier overnight continuation.

**Expected.** The new punch belongs to the incoming Manila assignment on December 11. A stale explicit choice should be rejected and leave the original sessions intact. The handoff contract sets the cutoff at midnight in the incoming zone. The explicit historical choice is reserved for an eligible continuation. [Handoff contract](../../features/attendance-interface.md#policy-settings) · [Punch contract](../../features/attendance-backend.md)

**Actual.** Current preview returned HTTP 200 with the incoming assignment and work date December 11. The explicit punch returned 201 and attached a second persisted session to December 10 under the outgoing UTC assignment. After closing that session, an implicit clock-in at `17:00Z` returned 201 under Manila for December 11, confirming the policy lookup worked. The explicit branch was reproduced in multiple independent fixture starts.

**Root cause.** With a supplied ID the service uses the selected workday's timezone to decide whether it is “today” and does not tie that ordinary day to the effective assignment at the new instant. The session trigger resolves the effective policy only when no workday ID is supplied. When supplied it checks ownership and time integrity, so the old but owned record is accepted. [Clock-in branch](../../../apps/api/src/features/attendance/attendance.service.ts#L233) · [Session trigger](../../../apps/api/prisma/migrations/20261121120000_attendance_policy_timezone_handoff/migration.sql)

**Resolution and regression.** Validate the chosen workday against the same effective assignment/date used for implicit clock-in, with a separately validated overnight continuation. Add one API test with pre-cutoff and exact-cutoff controls and assert the rejected call writes neither a session nor an audit event. Preserve permitted current-day split shifts and explicit overnight continuation. Verify both handoff directions and a different target in the outgoing policy to make incorrect downstream association observable. Review any additional direct session writers before tightening database behavior.

**Implemented fix.** The attendance service resolves the effective policy inside the existing employee-locked transaction, using the same server instant for the punch and for policy resolution. An ordinary explicit workday must match both the effective assignment ID and work date. The separately allowed continuation now requires a recorded session on that workday spanning local midnight. This prevents a day attributed to yesterday solely because of the handoff from qualifying. A qualifying earlier session keeps continuation available after another split session ends that morning. Current-state preview uses the same eligibility check as the write path. The fix is confined to the service and uses the existing database trigger and stored workday snapshots. [Attendance service](../../../apps/api/src/features/attendance/attendance.service.ts)

**Regression cases.** The existing policy-management test now exercises the explicit and implicit paths at the cutoff in both directions. The attendance backend test retains the real overnight continuation and additionally checks that it remains offered after the first follow-on split. [Policy handoff tests](../../../apps/api/tests/features/attendance/policy-management.test.ts) · [Overnight continuation test](../../../apps/api/tests/features/attendance/backend.test.ts)

**Verification.** Before the fix, the new assertions failed in both directions with HTTP 201 instead of 409 at the cutoff. After the fix, the last pre-cutoff explicit clock-in returned 201 on the outgoing workday, and the open session closed on that same workday at the cutoff. A new clock-in at the cutoff with the outgoing workday ID returned 409 and left full session and attendance audit snapshots identical. An implicit clock-in at the same instant used the incoming policy. History retained the outgoing 480-minute target and used the incoming 360-minute target for the new workday. Closing the incoming seven-hour session created one 60-minute overtime request linked to that session.

The attendance, policy, leave, overtime, reporting, and workload API selection passed all 76 tests, including Node parent tests. Web units passed all 130 tests and the production build passed. Three real-backend Chromium cases passed for overnight punching, unpaid breaks, and grouped route access. The exact handoff boundaries were verified through the API using migrated in-memory PGlite. Direct database writers, multi-connection races, and historical rows previously attributed through the defect remain outside this fix's verification.

### WC-02-F02 · High · Verified · Suspended shift recovery cannot be completed in the portal

**Reproduction.** As a linked Staff user, start a shift and an unpaid break. As Superadmin, deactivate the login via `PATCH /api/users/:id/status`, then reactivate it and authenticate again. Open Check-Ins as the employee. As Admin and Superadmin, open Time Logs Records and select that employee. The direct API fixture used a shift starting seven hours before the observation, a break starting 45 minutes before it, and a proposed closure 15 minutes before it.

**Expected.** A suspended shift is identifiable, and an authorized manager can select the open suspended session, confirm an end instant, provide a reason and resolve it in Time Logs. The new login can then start work. Existing authorization prevents self-service from closing this shift. [Reconciliation route](../../../apps/api/src/features/attendance/routes.ts#L122) · [Suspension and self-service guard](../../../apps/api/src/features/attendance/attendance.service.ts#L270)

**Actual.** The stored session retained `endedAt: null`, a non-null `suspendedAt`, and the still-open break. The employee saw “Clocked out” and “You already have an active attendance session” together, with a disabled Clock in and no Clock out control. Admin and Superadmin could open the employee's Time Logs Records. There was no Reconcile action, and the web client helper had no caller. An explicit employee clock-out or end-break request returned 409 instructing HR to reconcile in Time Logs. Admin's direct reconciliation returned 200, closed both the session and break at the confirmed instant, and enabled a new clock-in (201).

**Root cause.** The personal page interprets a logged workday with no active session as clocked out. The current endpoint returns a generic active-session block for a suspended open row. The manager Records UI never calls the existing reconciliation helper. This blocks a required manager workflow in the portal. The API recovery and its access rules are functional. [Personal rendering](../../../apps/web/src/features/attendance/pages/my-attendance-page.tsx#L153) · [Client helper](../../../apps/web/src/features/attendance/api/attendance-api.ts#L141)

**Resolution and regression.** Expose suspended state and accurate next steps on Check-Ins. Wire an existing manager Time Logs surface to the reconciliation API using the same permission and ownership checks, a confirmed end instant, and a required reason. After close, refresh the employee and manager views and verify terminal state/audit without repeating the write. Add one real-backend browser workflow covering deactivation, a new login, manager close and restored punching. Leave exhaustive role, ordering, and rollback cases in API coverage.

**Implemented fix.** Check-Ins and its history detail distinguish an open suspended session from a completed shift. Check-Ins directs the employee to HR and shows the blocked Clock in control until recovery. Time Logs → Records → View details shows Reconcile shift when the Records response marks the workday eligible and the session is still open and suspended. The Records projection uses existing employee-management permission and excludes the manager's own workday. Its ownership check uses the linked account internally. The write goes through the existing reconciliation endpoint and retains its authorization, ordering, audit and transaction rules.

The dialog starts with a blank clock-out, uses the shared date/time input in the device timezone, and requires a trimmed reason of 5–2,000 characters. It keeps entered values and shows the backend error on failure. A synchronous submission guard and disabled controls prevent duplicate requests in the dialog. Success refreshes Records. Check-Ins detects recovery through its existing visibility and polling refresh, and the suspended-state transition refreshes personal history.

**Affected files.** The Records capability is computed in the API management service using the existing reporting projection. The web changes cover the attendance DTO, session-state helper, Check-Ins, shared history table and details, and the new reconciliation form composed from the shared Modal, DateInput, FormTextarea and feedback components. Time Logs Records launches the form. The backend suite and offline browser fixture exercise the existing endpoint and recovered portal flow. [Management records](../../../apps/api/src/features/attendance/attendance.management.ts) · [Reporting projection](../../../apps/api/src/features/attendance/attendance.reporting.ts) · [Attendance DTO](../../../apps/web/src/features/attendance/api/attendance-api.ts) · [Session state](../../../apps/web/src/features/attendance/model/attendance.ts) · [Check-Ins](../../../apps/web/src/features/attendance/pages/my-attendance-page.tsx) · [History](../../../apps/web/src/features/attendance/components/attendance-history.tsx) · [History details](../../../apps/web/src/features/attendance/components/attendance-history-details-panel.tsx) · [Records](../../../apps/web/src/features/attendance/pages/attendance-records-page.tsx) · [Reconciliation dialog](../../../apps/web/src/features/attendance/components/attendance-reconciliation-dialog.tsx) · [API regression](../../../apps/api/tests/features/attendance/backend.test.ts) · [Browser regression](../../../apps/web/e2e/attendance.spec.ts) · [Browser fixture](../../../apps/api/tests/support/attendance-browser-server.ts)

**Verification.** Before the fix, the new Chromium workflow reached the employee's new login after deactivation and reactivation, then failed to find the suspended-state label. After the fix, the real Express/PGlite workflow passed. Staff and Head writes returned 403. Head saw no reconciliation control, and Admin and Superadmin saw the action for the suspended employee. The form required an explicit end and nonblank reason. The API returned 409 for an invalid end, and the dialog retained its inputs. A held real request showed disabled controls while submitting. One successful submission closed both the session and unpaid break, the refreshed Records removed the suspended status, and a duplicate API request returned 409. The employee's visibility refresh restored the Clock in button and a fresh punch succeeded. The targeted backend subtest checked own-shift denial, reason validation, capability removal on close, and audit actor and reason.

The attendance, leave, workload, and account status and restore API selection passed 79 tests, counting Node parent tests. All 130 web unit tests and five selected real-backend Chromium cases passed. The production build passed. The browser workflow uses a synthetic account and the real login, account-status, attendance and reconciliation APIs. Unrelated shell requests use fixture responses. Remaining verification limits include the device-local picker's repeated-hour interpretation, workdays outside the default Records date filter, and multi-connection PostgreSQL races.
