## Confirmed findings

### WC-01-001 · High · Verified · Scheduled unassign leaves coverage active at a repeated midnight

**Reproduce.** In the migrated fixture, retain an existing assignment, then schedule an `America/Havana` replacement for 2026-11-01. Set the server clock to `2026-11-01T04:30:00.000Z`, during the first occurrence of 00:30 local. Read the replacement through `GET /policies/:policyId/assignments`, then call its unassign endpoint. Read the assignment again and query the employee's `GET /me/current` at `05:00:00.000Z`.

**Expected.** An assignment already presented as `SCHEDULED` is cancelled and its predecessor restored under the normal cancellation rules.

**Before the fix.** The directory initially returned `SCHEDULED`. Unassign returned 200, and the next directory read still returned `SCHEDULED` with `effectiveUntil: 2026-11-02`. At `05:00Z` personal attendance returned HTTP 200 and selected the Havana policy on November 1.

**Root cause.** PostgreSQL resolves Havana's ambiguous midnight to the second occurrence, at `05:00Z`. The directory and effective policy lookup compare instants using that boundary. Unassign compared the assignment start date with the current date in Havana. That date already read November 1 during the first occurrence, so unassign entered the current-assignment branch.

**Implemented fix.** The directory and unassign share a PostgreSQL status expression using the policy's start instant and the existing successor-aware end function. Unassign reads the status inside the transaction after locking the employee. For future assignments, any submitted, verified, or approved leave referencing the assignment blocks cancellation, including leave on the repeated local date. Once those dependencies are resolved, the existing cancellation path retains terminal leave history or deletes an unreferenced assignment, restores the predecessor, and rewires the successor. For current assignments, the next local calendar day still determines the end date.

### WC-01-002 · High · Verified · Date-line replacement creates an assignment with no effective instant

**Reproduce.** With an existing employee policy, schedule `Pacific/Pago_Pago` for 2026-12-10 and then `Pacific/Kiritimati` for 2026-12-11. Both requests returned 201. Use the fixture clock to read both status rows and personal attendance at the instants below.

| UTC clock               | Pago Pago status | Kiritimati status | Effective workday and policy       |
| ----------------------- | ---------------- | ----------------- | ---------------------------------- |
| 2026-12-10 09:59:59.999 | Scheduled        | Scheduled         | December 9, original Manila policy |
| 2026-12-10 10:00:00.000 | Scheduled        | Current           | December 11, Kiritimati            |
| 2026-12-10 11:00:00.000 | Ended            | Current           | December 11, Kiritimati            |

**Expected.** Each accepted scheduled period has a positive effective duration. A conflicting replacement should return a clear conflict while preserving the prior assignments, unless a product decision defines another ordering rule.

**Before the fix.** The west-zone period was accepted and shortened to end on December 11. Its own start is 11:00 UTC on December 10, but its successor sets its end at 10:00 UTC that day. It transitions from Scheduled directly to Ended. Personal effective policy skips it and work date December 10.

**Root cause.** The API validates the incoming calendar date, then compares dates to determine which period it shortens. The database date constraint and overlap trigger also compare calendar dates. At read time, `attendance_assignment_end_at` uses the adjacent incoming policy's midnight as the predecessor's cutoff, including when the predecessor's stored end date was already set. That cutoff could be at or before the predecessor's own start instant. [Assignment mutation](../../../apps/api/src/features/attendance/attendance.management.ts) · [Date constraints](../../../apps/api/prisma/migrations/20261113150000_attendance_foundation/migration.sql) · [Cutoff and date-range trigger](../../../apps/api/prisma/migrations/20261121130000_attendance_assignment_cancellation/migration.sql)

**Implemented fix.** Inside the existing employee-locked transaction for `POST /assignments`, PostgreSQL computes both midnights using the same date-to-instant conversion as the effective-policy lookup. The API returns HTTP 409 if the new cutoff is at or before the start of a non-cancelled period that overlaps the incoming date or already ends on it. The check runs before any assignment or audit writes. Valid replacements keep the existing cutoff, linkage, and cancellation behavior. This fix requires zero schema or migration changes.

### WC-01-B01 · Resolved · Overtime inbox assertion blocked the short-shift check

The runner's emitted `overtime.test.js:243` maps to the requester inbox assertion at the original TypeScript line 356. **Root cause.** The migrated in-memory fixture creates separate Staff, Head, HR, outsider, and automatic-overtime employees with a 480-minute Manila policy. `automatic` earned three requests across the initial, split, and overnight sessions. The four notices are verification and approval of the first request, direct approval of the split-session request, and rejection of the overnight request. Commit `ff9ca943` added requester delivery for review stages and requester inbox access, while the older test still expected an empty inbox. The department handoff removes the former Head's access to reviewer notices and the active requester retains their own review notices. The attendance documentation defines automatic clock-out requests for whole excess worked minutes, excluding unpaid breaks. The fixture's 60-minute shift therefore has zero excess against its 480-minute target. The source and passing assertions establish a stale test expectation.
