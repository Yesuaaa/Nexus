# Phase 1 — Page Authorization Matrix

## Enforcement layers

1. The root layout applies AuthProvider. The portal layout loads the current account and applies isRouteDenied before showing portal content. These are frontend session/navigation controls, not API authorization.
2. Route policy is defined in apps/web/src/features/workspaces/model/route-policy.ts and its helpers in apps/web/src/features/auth/model/permissions.ts. Module availability is defined in apps/api/src/features/modules/module-registry.json and imported by the web registry.
3. Express independently checks Bearer session state, roles, permissions, capabilities, and record/workflow scope in feature controllers/services. A visible link or a successful route-policy check does not grant API access.

## Fixed role baseline

| Role       | Source-defined permission summary                                                                                         | Operational scope                                                                                                                                        |
| ---------- | ------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| USER       | Dashboard/profile/common self-service permissions                                                                         | Own client/service requests, own client decisions, own project records                                                                                   |
| STAFF      | Common permissions plus department read                                                                                   | Own employee self-service; assigned project/workspace and department-head workflows only where current assignment/headship permits                       |
| ADMIN      | Department/service/client/employee management plus payroll read/manage                                                    | Feature scope is still enforced; ADMIN does not get global administration or operational membership by role alone                                        |
| SUPERADMIN | ADMIN feature grants plus account management, global module/organization/administration/conversation grants, payroll read | Broad administrative inspection; payroll management is not granted; global admin role does not itself create operational project/request/client identity |

Evidence: apps/api/src/features/auth/auth.permissions.ts:46-100; apps/api/src/features/auth/auth.capabilities.ts; apps/web/src/features/auth/model/roles.ts; apps/web/src/features/auth/model/permissions.ts.

## Alias access

The aliases are inside the portal route group and therefore do not become public routes. Route policy declares legacy attendance/payroll paths explicitly. AL-001 uses personal attendance eligibility; AL-002 and AL-008 use active STAFF self-payroll eligibility; AL-003 and AL-005 use attendance configuration eligibility; AL-004 and AL-006 use attendance manager eligibility; AL-007 is STAFF workspace access. Alias redirects do not transfer API authorization to their target.

## Backend authorization boundary

API authorization is independently established at domain route/service level. Examples verified in source:

- User/account routes use a Superadmin router gate and separate policy checks: apps/api/src/features/users/users.controller.ts and users.service.ts.
- Payroll routes check payroll read/manage capability; Superadmin is read-only for payroll: apps/api/src/features/payroll/payroll.controller.ts and apps/api/src/features/auth/auth.capabilities.ts.
- Attendance and leave operations validate employee, department, supervisor/head, ownership, and workflow stage in their routers/services.
- Project and conversation APIs distinguish administrative visibility from owning client, assigned staff, workspace membership, and conversation participation.
- Log viewers are Superadmin-gated; a frontend route permission does not grant access to log data.
