# Phase 1 — Page and Component Mapping

This document follows each PG identifier from its App Router entry file to the first behavior-owning component or inline page implementation. Shared layout/provider relationships are recorded separately. A component entry point is source evidence; it does not prove that every nested interaction works.

## Shared layout and provider chain

| Scope                 | Source chain                                                                                                                      | Responsibilities established from source                                                                         |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| All routes            | apps/web/src/app/layout.tsx → AuthProvider                                                                                        | Root HTML, Inter font setup, global styles, shared auth provider                                                 |
| Auth group            | (auth) route file → features/auth/pages/auth-page.tsx → AuthPage → AuthFormPage → AuthLayout, AuthContent, AuthHeader, PhotoPanel | Client/internal login and registration modes; session recheck and role landing; auth form and language selection |
| Portal group          | (portal) route file → apps/web/src/app/(portal)/layout.tsx → PortalLayout                                                         | Current account loading, client-side denial redirects, sign-out and portal shell                                 |
| Authenticated account | PortalLayout → AccountContext → PreferencesProvider → BreadcrumbLabelProvider                                                     | Current-account, preferences, and breadcrumb state passed to descendants                                         |
| Internal workspace    | PortalLayout → WorkspaceProvider → RoleLayout or WorkspaceSelectorShell                                                           | Workspace state is present for non-USER roles; /module uses the selector shell                                   |
| Portal role shell     | PortalLayout → RoleLayout                                                                                                         | Role-dependent shell/sidebar and authenticated portal framing                                                    |

Evidence: apps/web/src/app/layout.tsx:1-31; apps/web/src/app/(portal)/layout.tsx:1-9; apps/web/src/components/layout/portal-layout.tsx:19-75; apps/web/src/features/auth/pages/auth-page.tsx:1-170.

## Alias implementation

AL-001–AL-008 contain no independent feature component. Each page file calls Next.js redirect() to the target listed in the route inventory. Alias source code is not counted as an additional rendered feature.

## Component limitations

This map follows route file → primary page component and shared layouts/providers. Feature folders own their local forms, dialogs, tables, hooks, validation, and API clients. Those leaf-level imports are not flattened into a full dependency graph here because doing so would obscure the behavior owners. Use PHASE_1_PAGE_FUNCTIONALITY_INVENTORY.md and PHASE_1_PAGE_API_DEPENDENCIES.md to continue at the feature boundary. A leaf relationship not listed there remains UNVERIFIED, rather than inferred from a folder name.
