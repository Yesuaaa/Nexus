## Route composition, providers, and access

- `apps/web/src/app/(portal)/attendance/adjustments/page.tsx:1-4` renders the page component without query parsing or route-mode props.
- The portal route is wrapped by `PortalLayout` (`apps/web/src/components/layout/portal-layout.tsx:21-79`). It loads the signed-in account through `useAccount`, shows shared loading/error states, redirects denied accounts, and provides `AccountContext`, `PreferencesProvider`, `BreadcrumbLabelProvider`, `WorkspaceProvider`, and `RoleLayout`.
- `/attendance/adjustments` has an exact route-policy entry (`apps/web/src/features/workspaces/model/route-policy.ts:420-424`) guarded by `canAccessAttendance`. This allows active STAFF and ADMIN, plus active SUPERADMIN with `employees:read`; USER and inactive or insufficiently privileged accounts are denied by the shared portal route gate. The route policy also associates the route with `attendance-monitoring`.
- The page uses `canManageAttendance` and `canAccessPersonalAttendance` (`apps/web/src/features/auth/model/permissions.ts:92-116`). A manager is an active STAFF department head, or an ADMIN/SUPERADMIN with `employees:read`. Self-service is active STAFF/ADMIN. A manager with self-service starts in team scope and may switch to personal scope; a manager without self-service (SUPERADMIN) stays in team scope; a non-manager self-service account starts in personal scope.
- The route is not emitted as its own sidebar link. The Request & Approvals group is built from `attendanceNavigation` and filters its links through `canAccessRoute` (`apps/web/src/features/attendance/model/navigation.ts:43-68`; `apps/web/src/components/layout/sidebar.tsx:563-580`). Direct navigation to PG-004 is still subject to the exact route policy.

## Page structure and behavior

`AttendanceAdjustmentsPage` composes `AttendanceShell`, `SearchField`, `FilterSelect`, `ManagementViewToggle`, `ResourceStatus`, `AttendanceAdjustmentTable`, `AttendancePagination`, `AdjustmentDialog`, and `AttendanceAdjustmentReviewPanel`. The shell labels the default route **Requests & Approvals** (`attendance-shell.tsx:49-54, 94-101`). The table displays employee, request type, start/end in the browser device timezone, reason, status, and row actions.

## API and persistence map

| Operation          | Web client                                                  | API route / service                                                                                                                   | Persistence and security                                                                                                                                                                               |
| ------------------ | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| List               | `attendanceAdjustments` (`attendance-api.ts:406-427`)       | `GET /attendance/adjustments` (`routes.ts:112-113`) → `adjustments` (`attendance.management.ts:1416-1504`)                            | Reads `AttendanceAdjustment` with employee/requester/reviewer relations; applies mine/team scope, type/status/search, stable ordering, and capability derivation in a repeatable-read transaction.     |
| Linked detail only | `attendanceAdjustmentDetail` (`attendance-api.ts:400-404`)  | `GET /attendance/adjustments/:adjustmentId` (`routes.ts:104-110`) → `adjustmentDetail` (`attendance.management.ts:1327-1377`)         | Applies requester/employee/head/HR/Superadmin visibility and returns approve/verify/reject capabilities. PG-004's ordinary details action does not call this route; stale overtime recovery does.      |
| Submit correction  | `requestAttendanceAdjustment` (`attendance-api.ts:429-439`) | `POST /attendance/adjustments` (`routes.ts:115-119`) → `requestAdjustment` (`attendance.management.ts:1506-1598`)                     | Transaction validates caller's employee ownership, request UUID/idempotency payload, timestamps, correction/session conflicts and reason; creates PENDING row and pending-review notification.         |
| Review             | `reviewAttendanceAdjustment` (`attendance-api.ts:441-452`)  | `POST /attendance/adjustments/:adjustmentId/review` (`routes.ts:120-128`) → `reviewAdjustment` (`attendance.management.ts:1600-1805`) | Transaction locks department, employee, user, and adjustment; checks placement, ownership, authority and stage; updates verification/review metadata and correction attendance only at final approval. |

The `AttendanceAdjustment` model records request key, employee, optional session/original snapshot, proposed timestamps, reason, type, overtime minutes, status, requester, verifier and reviewer metadata, and timestamps; it relates to `Employee`, `AttendanceWorkSession`, `User` requester/reviewer/verifier, and workflow notifications (`apps/api/prisma/schema.prisma:1599-1634`). Statuses are PENDING, VERIFIED, APPROVED, REJECTED. API routes use the authenticated user from `req.auth!.user.id`.
