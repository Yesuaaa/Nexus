## Authorization and contract notes

- Current identity policy is clear: USER is the Client Dashboard actor. STAFF, ADMIN, and SUPERADMIN use the internal workspace selector. Anonymous visitors authenticate through /login.
- GET /api/auth/me requires profile:read. dashboard:read is part of the fixed common permissions, but the Dashboard route policy does not call that permission helper. The current source applies the role check in PortalLayout and DashboardPage; no separately editable Dashboard grant was found. Do not treat this as a confirmed authorization defect or fabricate a per-user permission fixture.
- Notification endpoints require authenticated sessions and derive userId from request.auth. Client notification visibility is resource-scoped by the actual clientId and event.internal=false.
- The Messages topbar calls request- and project-conversation list APIs. Their controllers require authenticated USER/STAFF contexts as appropriate; service predicates scope request conversations and active client-owned project membership. Project unread counts use client-visible message predicates. The combined two-Client list/count assertion remains a planned PGlite gap, not a confirmed disclosure.
- The current event-link fallback routes other notification types to /messages?request=; a missing requestId becomes an empty query value. No product rule for unknown event types or absent requestId was identified. Test a known Client producer event; do not invent a universal event taxonomy.
- Repeated single-read calls update readAt again, but the established invariant is read/unread state and recipient scope. No requirement to preserve the first timestamp was found.
- No confirmed PG-020 security or application defect is established by source inspection.

## Dependencies and scope boundaries

The route depends on AccountContext/PortalLayout and shared navigation. Notifications depend on request-workflow authentication, WorkflowNotification visibility, event summary/type/entityId, and user preference settings. MessagesLink depends on request- and project-conversation list APIs. Its unread count is shared shell behavior; conversation message content and destination access remain owned by their respective PG records.

The historical Phase 1 route mapping is preserved as written. This discovery documents the card/API discrepancy without changing Phase 1 documents or renumbering the page.
