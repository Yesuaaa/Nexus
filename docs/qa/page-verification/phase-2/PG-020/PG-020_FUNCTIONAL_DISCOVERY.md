## Phase 1 reconciliation

The registry correctly identifies PG-020 as /dashboard and USER as its eligible role. The older functionality and API-dependency inventories describe “client workspace/service cards,” client/project/service data APIs, and an unverified card endpoint closure. Current DashboardPage contains only a labelled main region and a PageHeader that directs Clients to the navigation menu. It does not render those cards and does not import a dashboard data API. The current page source and its explicit navigation description are therefore the basis for this design. Tests for missing cards or data summaries would require a product decision; no absent behavior is invented here.

The route policy’s /dashboard row has no module and a permissive route predicate, but PortalLayout redirects non-USER roles and the component independently returns null for non-USER. The separate /module route is internal-only. The user role permission set includes dashboard:read; the application has no per-user dashboard permission editor identified in this trace. Do not fabricate an unsupported permission configuration to test.

## Current controls and absent behavior

The Dashboard body has no search, filter, sort, pagination, create/edit/archive/delete control, upload/download, confirmation dialog, card action, or refresh control. Navigation links and the shared topbar are the implemented user controls. Notifications are the only dashboard-shell feature that changes persistent business-facing state, by writing readAt. The page itself does not write client, project, service, or workflow data.

## Source-backed invariants

- A valid USER account reaches the Client Dashboard; authenticated internal roles are routed to /module; anonymous access is sent to the client sign-in path.
- The page remains absent while account state is unresolved or failed, and an expired session cannot display a stale account shell.
- A Client’s workflow notification list contains only notices visible to that authenticated Client, including non-internal events for owned requests.
- A Client cannot mark another recipient’s notification read by changing the path identifier.
- Mark-all affects only the authenticated recipient’s currently visible unread notices.
- Listing is bounded to 40 rows while unreadCount covers all visible unread rows; ordering is deterministic.
- Dashboard is a navigation hub. No card, analytics, or data-summary behavior is asserted.
