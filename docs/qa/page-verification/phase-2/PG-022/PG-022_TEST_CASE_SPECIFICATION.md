## Case objective, priority and abuse mapping

Priority is a future execution order, not a severity or defect finding. P1 covers access/privacy, read integrity, role transition, inert output and correctness of the main figures. P2 covers other page behavior, recovery, accessibility/responsive coverage, transport evidence and contracts awaiting a product oracle. A mapped hypothesis can span cases; mapping does not imply the case alone proves every part of that hypothesis. A dash means no direct abuse hypothesis is assigned. Abuse IDs are abbreviated here as ABUSE-###; their full stable form is PG-022-ABUSE-###.

## Fixtures and cleanup

Browser tests use synthetic account/settings/list responses through regression support. API tests use locally issued sessions and startPgliteApp, whose migrations and teardown are scoped to in-memory PGlite. Compare before/after domain/history state for denial and read-only checks. Use accessible locators and response/settled-state waits. No production data, external notifications, real database, or user-owned process is used. Existing-sufficient means assertions match the stated invariant; no case is a fresh PG-022 run.
